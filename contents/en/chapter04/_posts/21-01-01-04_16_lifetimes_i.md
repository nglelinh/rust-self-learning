Lifetimes are how Rust proves references are always valid, even across complex control flow. This lesson builds the mental model: lifetimes are about **relationships between references and the data they point to**, not about "how long the program runs".

## 60-minute teaching plan

- 0 to 10 min: Why lifetimes exist (prevent dangling references).
- 10 to 25 min: References, scopes, and the "borrowed value does not live long enough" error.
- 25 to 40 min: Lifetime elision rules (what Rust infers).
- 40 to 60 min: Mini-lab: implement `longest` variations + explain each signature.

## Learning goals

By the end of this lesson, students can:

- Explain what lifetimes represent (a constraint, not a runtime value).
- Identify dangling-reference scenarios.
- Understand when Rust can infer lifetimes (elision) and when you must annotate.
- Write and explain the classic `longest` function signature.

## Key concept: what is a lifetime, really?

A common misconception: *"lifetime `'a` is the duration the data lives in memory."*

That is wrong. A **lifetime parameter is a constraint on the relationship between references**. It tells the borrow checker: "the thing I return must not outlive the things I borrow from."

Think of it like a label on a group of references:

> "All references tagged `'a` must be valid for the same overlapping region of code."

The compiler shrinks the region to the smallest intersection. No runtime cost. No timer.

Another analogy: if you borrow a library book, you can't keep reading it after returning it. The library doesn't need a timer — the rule is enforced by policy. Rust enforces the "return the book" rule at compile time.

## The problem: dangling references

This code is invalid because it returns a reference to a value that will be dropped:

```rust
fn bad() -> &str {             // error: missing lifetime specifier
    let s = String::from("hello");
    s.as_str()                 // s is dropped at end of function
}                              // reference would dangle
```

Rust rejects it because `s` is dropped at the end of `bad`, and the returned `&str` would point to freed memory — exactly the use-after-free bug that ends C programs.

### What the error says

```
error[E0106]: missing lifetime specifier
 --> src/main.rs:1:13
  |
1 | fn bad() -> &str {
  |             ^ expected named lifetime parameter
```

The compiler is telling you: "I don't know how long this `&str` should be valid." And the honest answer is: it *can't* be valid at all, because the backing `String` is local.

## Lifetimes as relationships

A lifetime parameter like `'a` means: "these references are tied together." It does not create a timer.

### The classic example: `longest`

We want: return a reference to the longer input slice. The returned reference must be valid for as long as **both** inputs are valid.

```rust
fn longest<'a>(a: &'a str, b: &'a str) -> &'a str {
    if a.len() >= b.len() { a } else { b }
}
```

Teaching points:

- `'a` is the **lifetime of the returned reference**.
- Both inputs are constrained to live at least `'a`.
- This does not mean both inputs have the same *actual* lifetime; it means the returned value cannot outlive **either** input.
- The compiler picks the **shorter** of the two actual lifetimes as the effective `'a`.

### Visualizing the constraint

```
let s1 = String::from("long string");     // 'a starts
{
    let s2 = String::from("xy");          // 'b starts (shorter)
    let result = longest(&s1, &s2);       // 'a = min('a, 'b) = 'b
    println!("{result}");                 // ok: result used inside 'b
}                                         // 'b ends
// result can't be used here — 'a is gone
```

## Lifetime elision rules (what Rust assumes)

Rust can often infer lifetimes in function signatures, so you don't need to write them. This is called **lifetime elision**.

Rule summary (enough for most day-to-day code):

1. Each reference parameter gets its own independent lifetime parameter.
2. If there is **exactly one** input lifetime, it is assigned to the output lifetime.
3. If there are **multiple** input lifetimes and one parameter is `&self` or `&mut self`, the output is tied to `self`.

### Examples where elision applies

```rust
// Rule 2: one input lifetime → assigned to output (but output is usize, not a ref)
fn len(s: &str) -> usize { s.len() }
```

No output lifetime needed because output is not a reference.

```rust
// Rule 2: one input → output gets same lifetime
fn first_char(s: &str) -> Option<char> { s.chars().next() }
```

No lifetime needed: `char` is `Copy`, owns its value.

```rust
// Rule 3: method, output tied to &self
impl Cache {
    fn get_entry(&self) -> &Entry { &self.entry }
}
```

### Where elision fails

```rust
// Two inputs — compiler can't guess which one the output references
fn longest(a: &str, b: &str) -> &str { ... }
// error[E0106]: missing lifetime specifier
```

This is why `longest` needs explicit lifetimes.

## Common compiler error: "does not live long enough"

Teach students to look for:

- a reference that **escapes the scope** of its owner
- returning references to locals or temporaries

### The "escaping local" pattern

```rust
fn pick<'a>(s: &'a str) -> &'a str {
    let t = String::from("temp");
    if s.len() > 0 { s } else { t.as_str() }
    //                         ^^^^^^^^^^^ error: `t` dropped while borrowed
}
```

This fails because `t.as_str()` would return a reference to a local `String` that is dropped when `pick` returns. The compiler tracks this and refuses.

### Fix options

Option 1: Return owned data when you might need to create it:

```rust
fn pick_owned(s: &str) -> String {
    if s.is_empty() { "fallback".to_string() } else { s.to_string() }
}
```

Option 2: Require the caller to provide the fallback:

```rust
fn pick_or<'a>(s: &'a str, fallback: &'a str) -> &'a str {
    if s.is_empty() { fallback } else { s }
}
```

Teaching point: the choice between options depends on who has the data the caller wants to return. When in doubt, owned is simpler.

## Code walkthrough: lifetime errors as teaching moments

### Naive attempt

```rust
fn headers(req: &Request) -> Vec<&str> {
    req.raw.split("\r\n").collect()
}
```

This works fine — the returned `&str` slices all borrow from `req.raw`, and elision handles it.

### The trouble starts when you store the result

```rust
fn bad_cache(req: &Request) -> Vec<&str> {
    let lines = req.raw.split("\r\n").collect::<Vec<_>>();
    // oops: lines is dropped at end of function, but &str borrowed from it
    lines.iter().map(|s| *s).collect()
}
```

This is actually fine because `split` returns slices of `req.raw`, not `lines`. But trying to return slices of a local `Vec<String>` would fail:

```rust
fn bad_local(req: &Request) -> Vec<&str> {
    let owned: Vec<String> = req.raw.split("\r\n")
        .map(|s| s.trim().to_string())
        .collect();
    owned.iter().map(|s| s.as_str()).collect()
    // error: `owned` dropped here — returned &str would dangle
}
```

Fix: return `Vec<String>`:

```rust
fn cleaned_headers(req: &Request) -> Vec<String> {
    req.raw.split("\r\n")
        .map(|s| s.trim().to_string())
        .collect()
}
```

## Mini-lab: `longest` variations

### 1. Two inputs, one output

```rust
fn longest<'a>(a: &'a str, b: &'a str) -> &'a str {
    if a.len() >= b.len() { a } else { b }
}
```

### 2. Tie output to the first input only

Sometimes you want "always return something derived from `a`".

```rust
fn prefix<'a>(a: &'a str, n: usize, _b: &str) -> &'a str {
    // Advance n char boundaries into a, return the prefix
    let end = a.char_indices().nth(n).map_or(a.len(), |(i, _)| i);
    &a[..end]
}
```

Teaching point: `_b: &str` is not tied to `'a`; it's irrelevant to the output.

### 3. Return owned instead of borrowed

When lifetime constraints become awkward, returning an owned value is almost always correct:

```rust
fn longest_owned(a: &str, b: &str) -> String {
    if a.len() >= b.len() { a.to_string() } else { b.to_string() }
}
```

Tradeoff: one allocation, but lifetimes vanish from the signature. Prefer this whenever performance is not the constraint.

## Applications in systems programming

### Parser buffers (zero-copy tokenizer)

Lexers and parsers are the canonical lifetime use case. Instead of allocating every token as a `String`, return slices of the input buffer:

```rust
struct Token<'src> {
    kind: TokenKind,
    text: &'src str,
}

fn tokenize<'src>(src: &'src str) -> Vec<Token<'src>> {
    // each Token borrows from src — zero allocations for the text
    todo!()
}
```

The lifetime `'src` encodes the contract: tokens cannot outlive the source string.

### Network protocol parsing

Same pattern for reading network frames from a byte buffer:

```rust
struct Frame<'buf> {
    header: &'buf [u8],
    body:   &'buf [u8],
}
```

The frame is a view into the network receive buffer — no copy.

### Configuration readers

A config file reader that returns key/value slices into an `mmap`'d buffer avoids all allocations while the buffer is live.

## Recap

- Lifetimes are compile-time constraints, not runtime timers.
- Lifetime parameters describe relationships between references.
- Elision handles many cases; annotate when output depends on multiple inputs.
- "Does not live long enough" means a reference escapes its owner's scope.
- When lifetime constraints become painful, consider returning owned data.
