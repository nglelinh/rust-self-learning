Real async code needs timeouts, cancellation, and careful handling of shared state. This lesson focuses on patterns that keep async systems reliable: structured tasks, avoiding holding locks across `.await`, and building event loops that can shut down gracefully.

## Key concept: async failure modes you must defend against

In synchronous code, a blocking call either returns or blocks forever. In async code, there are several additional failure modes:

| Failure mode | Symptom | Cause |
|---|---|---|
| **Hung future** | Task never wakes | IO callback never fires; no timeout |
| **Stalled task** | Task never runs | CPU-heavy code hogging the executor |
| **Infinite retry** | CPU spins | Missing backoff or missing error check |
| **Lock starvation** | Low-priority task waits forever | High-priority tasks hold lock through many awaits |
| **Task leak** | Memory grows | Spawned tasks that never complete or get dropped |

Defensive async design means thinking about each of these upfront.

## Timeouts (repeat the rule)

**Rule: every external call must have a timeout.**

Network, disk, timer — if it can hang, it will hang. Without timeouts, a single slow dependency can stall your entire system.

### Basic timeout wrapper

```rust
use tokio::time::{timeout, Duration};

async fn with_timeout<T, E>(
    operation: impl std::future::Future<Output = Result<T, E>>,
    secs: u64,
) -> Result<T, String>
where
    E: std::fmt::Display,
{
    match timeout(Duration::from_secs(secs), operation).await {
        Ok(Ok(value))  => Ok(value),
        Ok(Err(e))     => Err(format!("operation failed: {e}")),
        Err(_elapsed)  => Err("timed out".to_string()),
    }
}
```

### Timeout with retry and exponential backoff

```rust
use tokio::time::sleep;

async fn retry_with_backoff<T, E>(
    mut f: impl FnMut() -> std::pin::Pin<Box<dyn std::future::Future<Output = Result<T, E>>>>,
    max_attempts: u32,
    base_delay_ms: u64,
) -> Result<T, E>
where
    E: std::fmt::Debug,
{
    let mut delay = base_delay_ms;
    for attempt in 0..max_attempts {
        match f().await {
            Ok(v) => return Ok(v),
            Err(e) if attempt + 1 == max_attempts => return Err(e),
            Err(e) => {
                eprintln!("attempt {attempt} failed: {e:?}, retrying in {delay}ms");
                sleep(Duration::from_millis(delay)).await;
                delay = (delay * 2).min(30_000);  // cap at 30 seconds
            }
        }
    }
    unreachable!()
}
```

Teaching points:

- Exponential backoff avoids thundering-herd when many clients retry simultaneously.
- Cap the max delay to avoid very long waits.
- `jitter` (random delay variation) further reduces thundering herd — a production concern.

## Cancellation and shutdown

In Rust async, "cancellation" is typically **cooperative**:

- When a task is dropped, its future is dropped at the next `.await`.
- Cancellation points happen at every `.await`.
- Tasks that never reach `.await` cannot be cancelled.

### Design tasks to reach `.await` regularly

```rust
// Bad: CPU-heavy loop in async context — no yield points!
async fn sum_bad(xs: &[u64]) -> u64 {
    let mut total = 0u64;
    for x in xs {
        total += x;  // no .await — this blocks the executor thread
    }
    total
}

// Good: use spawn_blocking for CPU work
async fn sum_good(xs: Vec<u64>) -> u64 {
    tokio::task::spawn_blocking(move || xs.iter().sum()).await.unwrap()
}
```

### Shutdown via `CancellationToken`

The `tokio-util` crate provides `CancellationToken` — the standard way to propagate shutdown:

```rust
use tokio_util::sync::CancellationToken;

let token = CancellationToken::new();

// Clone for each worker
let worker_token = token.clone();
tokio::spawn(async move {
    tokio::select! {
        _ = worker_token.cancelled() => {
            println!("worker received shutdown signal");
        }
        _ = do_work() => {
            println!("work completed naturally");
        }
    }
});

// Trigger shutdown
tokio::time::sleep(Duration::from_secs(5)).await;
token.cancel();
```

### Shutdown via channel

A simpler alternative without `tokio-util`:

```rust
use tokio::sync::watch;

let (stop_tx, stop_rx) = watch::channel(false);

tokio::spawn(async move {
    let mut stop_rx = stop_rx.clone();
    loop {
        tokio::select! {
            _ = stop_rx.changed() => {
                if *stop_rx.borrow() { break; }
            }
            event = receive_event() => process(event),
        }
    }
});

// Signal shutdown
stop_tx.send(true).unwrap();
```

`watch::Sender` broadcasts to all receivers — useful when many tasks need to observe the same shutdown signal.

## The lock + await pitfall

This is one of the most common async bugs:

```rust
use tokio::sync::Mutex;
use std::sync::Arc;

async fn bad(shared: Arc<Mutex<Vec<u8>>>) {
    let mut guard = shared.lock().await;  // lock acquired
    // ... some work ...
    tokio::time::sleep(Duration::from_secs(1)).await;  // suspended while lock held!
    guard.push(1);
}
```

Why it's bad:

- You hold the Tokio `Mutex` for the entire duration of the sleep.
- Other tasks that need this lock are blocked for 1 second.
- Worse with `std::sync::Mutex`: you can deadlock the executor.

### The `std::sync::Mutex` + `.await` danger

`std::sync::Mutex` is not `Send` across `.await` because Rust cannot guarantee the guard will be dropped before the task is moved to another thread. The compiler will reject it:

```
error: future cannot be sent between threads safely
   because `MutexGuard<Vec<u8>>` is not `Send`
```

### Fix: keep lock scope small

```rust
async fn better(shared: Arc<Mutex<Vec<u8>>>) {
    // Option 1: drop the guard explicitly before awaiting
    {
        let mut guard = shared.lock().await;
        guard.push(1);
    }  // guard dropped here — lock released

    tokio::time::sleep(Duration::from_millis(10)).await;  // no lock held
}

// Option 2: extract what you need before awaiting
async fn better_v2(shared: Arc<Mutex<Vec<u8>>>) {
    let len = shared.lock().await.len();  // lock released after .len()
    tokio::time::sleep(Duration::from_millis(10)).await;
    shared.lock().await.push(len as u8);
}
```

### Use `tokio::sync::Mutex` for async contexts

```rust
use tokio::sync::Mutex;

// tokio::Mutex is Send — safe to hold across .await
let shared = Arc::new(Mutex::new(vec![]));
let mut guard = shared.lock().await;
some_async_work().await;   // safe — guard is tokio's
guard.push(1);
```

But even then: don't hold it longer than necessary. Long lock times reduce concurrency.

## Mini-lab: merge two event sources with shutdown

We will simulate two sources using timers and channels, then build a loop that consumes both and supports graceful shutdown.

### Step 1: define the message type

```rust
#[derive(Debug, Clone)]
enum Event {
    SourceA { seq: u64 },
    SourceB { seq: u64 },
}
```

### Step 2: create source tasks

```rust
use tokio::sync::mpsc;
use tokio::time::{sleep, Duration};

async fn source_a(tx: mpsc::Sender<Event>, count: u64) {
    for seq in 0..count {
        sleep(Duration::from_millis(80)).await;
        if tx.send(Event::SourceA { seq }).await.is_err() {
            break;  // receiver dropped — stop
        }
    }
}

async fn source_b(tx: mpsc::Sender<Event>, count: u64) {
    for seq in 0..count {
        sleep(Duration::from_millis(130)).await;
        if tx.send(Event::SourceB { seq }).await.is_err() {
            break;
        }
    }
}
```

Teaching points:

- Check send errors — the receiver may be dropped (shutdown).
- Using Tokio's async `mpsc`, not std's blocking one.
- Different intervals create realistic interleaving.

### Step 3: the merge loop with timeout-based shutdown

```rust
use tokio::time::timeout;

async fn run_event_loop(
    mut rx:       mpsc::Receiver<Event>,
    idle_timeout: Duration,
) -> u64 {
    let mut count = 0u64;
    loop {
        match timeout(idle_timeout, rx.recv()).await {
            Ok(Some(event)) => {
                count += 1;
                println!("[{count}] {:?}", event);
            }
            Ok(None) => {
                println!("all sources finished");
                break;
            }
            Err(_elapsed) => {
                println!("idle for {:?} — shutting down", idle_timeout);
                break;
            }
        }
    }
    count
}
```

Teaching points:

- `Ok(None)` means all senders were dropped — channel closed naturally.
- `Err(_elapsed)` means no event arrived within the timeout — idle shutdown.
- This is a clean "two-exit" design: natural finish or timeout.

### Step 4: wire it all together

```rust
#[tokio::main]
async fn main() {
    let (tx, rx) = mpsc::channel(100);

    let h_a = tokio::spawn(source_a(tx.clone(), 5));
    let h_b = tokio::spawn(source_b(tx.clone(), 5));
    drop(tx);  // important: drop the original sender so the channel closes when both sources finish

    let total = run_event_loop(rx, Duration::from_millis(500)).await;
    println!("processed {total} events");

    // Wait for both sources to finish
    let _ = tokio::join!(h_a, h_b);
}
```

### Step 5: tests

```rust
#[cfg(test)]
mod tests {
    use super::*;

    #[tokio::test]
    async fn processes_all_events() {
        let (tx, rx) = mpsc::channel(100);
        tokio::spawn(source_a(tx.clone(), 3));
        tokio::spawn(source_b(tx.clone(), 3));
        drop(tx);
        let count = run_event_loop(rx, Duration::from_secs(2)).await;
        assert_eq!(count, 6);
    }

    #[tokio::test]
    async fn idle_shutdown_fires() {
        let (tx, rx) = mpsc::channel(100);
        // Don't send anything — idle timeout should trigger
        drop(tx);
        let count = run_event_loop(rx, Duration::from_millis(50)).await;
        assert_eq!(count, 0);
    }
}
```

## Code walkthrough: naive → idiomatic

### Naive: no cancellation, no timeout

```rust
async fn process_stream(mut rx: mpsc::Receiver<Request>) {
    while let Some(req) = rx.recv().await {
        handle_request(req).await;  // what if this hangs?
    }
}
```

If `handle_request` hangs (network timeout, deadlock), the loop stalls forever.

### Idiomatic: timeout + shutdown signal

```rust
use tokio::select;

async fn process_stream(
    mut rx:      mpsc::Receiver<Request>,
    mut stop:    watch::Receiver<bool>,
) {
    loop {
        select! {
            _ = stop.changed() => {
                if *stop.borrow() { break; }
            }
            result = timeout(Duration::from_secs(10), rx.recv()) => {
                match result {
                    Ok(Some(req)) => {
                        if let Err(e) = timeout(Duration::from_secs(5), handle_request(req)).await {
                            eprintln!("request timed out: {e}");
                        }
                    }
                    Ok(None) => break,          // channel closed
                    Err(_)   => eprintln!("receive timed out"),
                }
            }
        }
    }
}
```

Every async operation has a timeout. Shutdown is explicit and observable.

## Applications in systems programming

### API gateway

A gateway must handle slow upstreams gracefully:

```rust
async fn proxy_request(
    client_req: Request,
    upstream: &str,
) -> Response {
    match timeout(Duration::from_secs(30), forward(client_req, upstream)).await {
        Ok(resp) => resp,
        Err(_)   => Response::gateway_timeout(),
    }
}
```

### Database connection pool

Pool connections have idle timeouts and health-check heartbeats:

```rust
async fn keep_connection_alive(mut conn: DbConn, idle_timeout: Duration) {
    loop {
        match timeout(idle_timeout, conn.recv_query()).await {
            Ok(Some(q)) => conn.execute(q).await,
            Ok(None)    => break,      // client disconnected
            Err(_)      => {
                // Send heartbeat to keep connection alive
                if conn.ping().await.is_err() { break; }
            }
        }
    }
}
```

### Health checker

A background task that monitors services and restarts them on failure — with backoff:

```rust
async fn monitor(service: &str) {
    let mut delay = Duration::from_secs(1);
    loop {
        match timeout(Duration::from_secs(5), check_health(service)).await {
            Ok(Ok(())) => {
                delay = Duration::from_secs(1);  // reset backoff on success
            }
            _ => {
                eprintln!("{service} unhealthy — retrying in {:?}", delay);
                sleep(delay).await;
                delay = (delay * 2).min(Duration::from_secs(60));
            }
        }
    }
}
```

## Challenges and extensions

1. **`tokio::select!` with cancellation**: implement a function that runs two async operations and returns whichever completes first, cancelling the other.

2. **Backpressure**: add a `mpsc::sync_channel`-like bounded channel to the event loop. What happens when the buffer fills? How do you handle `SendError`?

3. **Structured concurrency with `JoinSet`**: use `tokio::task::JoinSet` to spawn tasks and collect their results, automatically cancelling remaining tasks if one fails.

4. **Tracing async spans**: add `tracing` instrumentation to the event loop. How do you track which event was being processed when a timeout fired?

## Common mistakes

1. **Infinite retries without backoff**: causes CPU spin and server hammering.
2. **Holding `std::sync::Mutex` across `.await`**: may deadlock or cause compile errors.
3. **No shutdown path**: tasks keep running forever, leaking resources.
4. **Forgetting to drop the extra sender**: the channel never closes, and `recv()` blocks forever.
5. **CPU-heavy code in async tasks**: stalls the executor thread, starving other tasks.

## Recap

- Timeouts and shutdown are not optional in real async systems.
- Cancellation is cooperative; tasks must reach `.await` to be cancelled.
- Never hold `std::sync::Mutex` guards across `.await` — use `tokio::sync::Mutex` or restructure.
- Structure async loops around typed message enums and explicit shutdown signals.
- Exponential backoff with a cap is the standard retry strategy.
