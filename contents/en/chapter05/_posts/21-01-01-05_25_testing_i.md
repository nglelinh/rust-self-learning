Testing in Rust is first-class, and good test structure keeps your refactors safe. This lesson teaches unit vs integration tests, how to test `Result`/error enums precisely, and how to design code so it's easy to test from the start.

## 60-minute teaching plan

- 0 to 10 min: Why testing matters in Rust (safe refactors, better design).
- 10 to 25 min: Unit tests: `#[test]`, module tests, common assertions.
- 25 to 35 min: Testing `Result` and typed errors.
- 35 to 50 min: Integration tests in `tests/`.
- 50 to 60 min: Mini-lab: add tests to parser/evaluator/config loader.

## Learning goals

By the end of this lesson, students can:

- Write unit tests for pure functions.
- Write tests that assert on `Result` error variants precisely.
- Create integration tests that use the public crate API.
- Refactor code to separate IO from logic for testability.

- Lesson 03-11/12 (Error Handling): `Result`, `?`, typed errors.

## Key concept: why testing in Rust is different

In many languages, tests are an afterthought because the compiler is lax. In Rust, the compiler already catches many bugs. So what do tests catch?

1. **Logic errors**: wrong computation, off-by-one, incorrect ordering.
2. **Invariant violations**: properties that should always hold across all inputs.
3. **Error paths**: the code that handles edge cases and errors is rarely exercised in development.
4. **Regression**: bugs you've already fixed and want to stay fixed.

The borrow checker and type system give you a floor — tests build the ceiling.

## Unit tests

Unit tests live next to the code they test, typically in the same file:

```rust
pub fn add(a: i32, b: i32) -> i32 {
    a + b
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn add_positive() {
        assert_eq!(add(2, 3), 5);
    }

    #[test]
    fn add_negative() {
        assert_eq!(add(-2, -3), -5);
    }

    #[test]
    fn add_overflow() {
        // i32::MAX + 1 overflows in debug mode → should panic
        // In release mode, it wraps. Test behavior matches your assumptions.
        assert_eq!(add(0, 0), 0);  // trivial, but documents the contract
    }
}
```

Teaching points:

- `#[cfg(test)]` ensures test code is compiled **only** in test builds — no production overhead.
- `use super::*;` brings items from the parent module into scope.
- Tests are functions with no return value that panic on failure.

### Running tests

```bash
cargo test           # run all tests
cargo test add       # run tests matching "add"
cargo test -- --nocapture   # show println! output
cargo test -- --test-threads=1   # run serially (useful for global state)
```

## Common assertions

### Basic

```rust
assert!(cond)                       // fails if cond is false
assert_eq!(a, b)                    // fails if a != b; prints both values
assert_ne!(a, b)                    // fails if a == b
assert!(s.contains("hello"))        // pattern assertion
```

### With custom messages

```rust
assert_eq!(result, expected, "processing '{}' failed", input);
```

Teaching point: always add a message when the assertion might not be self-explanatory.

### Testing panics

```rust
#[test]
#[should_panic(expected = "index out of bounds")]
fn access_out_of_bounds_panics() {
    let v = vec![1, 2, 3];
    let _ = v[10];
}
```

`expected` is a substring of the panic message. Use this for cases where panicking is the correct behavior.

## Testing `Result` and error enums

This is the most important testing pattern in Rust. Typed errors make failure paths testable and explicit.

### Setting up a typed error

```rust
#[derive(Debug, Clone, PartialEq, Eq)]
pub enum ParseError {
    Empty,
    InvalidNumber { input: String },
    OutOfRange { value: i64 },
}

pub fn parse_port(s: &str) -> Result<u16, ParseError> {
    let s = s.trim();
    if s.is_empty() {
        return Err(ParseError::Empty);
    }
    let n: i64 = s.parse().map_err(|_| ParseError::InvalidNumber {
        input: s.to_string(),
    })?;
    if n < 1 || n > 65535 {
        return Err(ParseError::OutOfRange { value: n });
    }
    Ok(n as u16)
}
```

### Tests: cover the happy path and every error variant

```rust
#[cfg(test)]
mod tests {
    use super::*;

    // Happy path
    #[test]
    fn valid_port() {
        assert_eq!(parse_port("8080"), Ok(8080));
        assert_eq!(parse_port("  443  "), Ok(443));  // whitespace trimmed
        assert_eq!(parse_port("1"), Ok(1));
        assert_eq!(parse_port("65535"), Ok(65535));
    }

    // Error: empty
    #[test]
    fn empty_input_returns_empty_error() {
        assert_eq!(parse_port(""), Err(ParseError::Empty));
        assert_eq!(parse_port("   "), Err(ParseError::Empty));
    }

    // Error: invalid number
    #[test]
    fn non_numeric_returns_invalid_number_error() {
        assert_eq!(
            parse_port("abc"),
            Err(ParseError::InvalidNumber { input: "abc".to_string() })
        );
    }

    // Error: out of range
    #[test]
    fn zero_is_out_of_range() {
        assert_eq!(parse_port("0"), Err(ParseError::OutOfRange { value: 0 }));
    }

    #[test]
    fn too_large_is_out_of_range() {
        assert_eq!(parse_port("65536"), Err(ParseError::OutOfRange { value: 65536 }));
        assert_eq!(parse_port("-1"), Err(ParseError::OutOfRange { value: -1 }));
    }
}
```

Teaching point: this is why typed errors (not `String` errors) matter — you can assert exact variants and fields. With `Err("invalid number".to_string())` you'd only check substring membership, missing the structured data.

### Testing `unwrap` is not the same as testing correctness

```rust
// This test passes, but it tests nothing about errors:
#[test]
fn bad_test() {
    let result = parse_port("8080");
    result.unwrap();  // panics on error, but you don't test the case where it shouldn't succeed
}

// Better:
#[test]
fn good_test() {
    assert_eq!(parse_port("8080"), Ok(8080));
}
```

## Integration tests

Integration tests live in `tests/` and use your crate **as an external user** would:

```
src/
  lib.rs
  parser.rs
tests/
  integration.rs
  cli.rs
```

### Example `tests/integration.rs`

```rust
// No `use super::*` — we're external, so we import by crate name
use my_crate::{parse_port, ParseError};

#[test]
fn integration_valid_port() {
    assert_eq!(parse_port("80"), Ok(80));
}

#[test]
fn integration_rejects_invalid() {
    assert!(matches!(
        parse_port("not-a-port"),
        Err(ParseError::InvalidNumber { .. })
    ));
}
```

Teaching points:

- Integration tests only see **public** items — this encourages good API design.
- Each file in `tests/` is an independent binary — they can't share code unless you create a module in `tests/common/mod.rs`.
- If your test file grows large, split it: each `tests/*.rs` file is a separate test binary.

### Multiple integration test files

```
tests/
  parsing.rs
  config.rs
  roundtrip.rs
```

`cargo test` compiles and runs all of them.

## Making code testable: isolate IO

The hardest code to test is code that mixes IO with logic.

### Hard to test: IO and logic together

```rust
pub fn load_config(path: &str) -> Result<Config, ConfigError> {
    let text = std::fs::read_to_string(path)?;  // IO
    parse_config(&text)                          // logic
}
```

Testing this requires actual files — slow, fragile, not portable.

### Easy to test: IO and logic separated

```rust
pub fn read_config_file(path: &str) -> Result<String, ConfigError> {
    std::fs::read_to_string(path).map_err(ConfigError::Io)
}

pub fn parse_config(text: &str) -> Result<Config, ConfigError> {
    // pure logic — no IO
    todo!()
}
```

Test the pure logic directly:

```rust
#[test]
fn parse_config_valid() {
    let text = "host=localhost\nport=8080";
    let cfg = parse_config(text).unwrap();
    assert_eq!(cfg.host, "localhost");
    assert_eq!(cfg.port, 8080);
}

#[test]
fn parse_config_missing_port() {
    let text = "host=localhost";
    let result = parse_config(text);
    assert_eq!(result, Err(ConfigError::MissingKey("port".to_string())));
}
```

## Mini-lab: add tests to a command parser

### The module under test

```rust
#[derive(Debug, Clone, PartialEq, Eq)]
pub enum Command {
    Get { key: String },
    Set { key: String, value: String },
    Delete { key: String },
    Quit,
}

#[derive(Debug, Clone, PartialEq, Eq)]
pub enum CommandError {
    Empty,
    UnknownCommand { cmd: String },
    MissingArgument { cmd: &'static str, arg: &'static str },
}

pub fn parse_command(input: &str) -> Result<Command, CommandError> {
    let parts: Vec<&str> = input.split_whitespace().collect();
    match parts.as_slice() {
        [] => Err(CommandError::Empty),
        ["get", key]   => Ok(Command::Get { key: key.to_string() }),
        ["get"]        => Err(CommandError::MissingArgument { cmd: "get", arg: "key" }),
        ["set", k, v]  => Ok(Command::Set { key: k.to_string(), value: v.to_string() }),
        ["set", _]     => Err(CommandError::MissingArgument { cmd: "set", arg: "value" }),
        ["set"]        => Err(CommandError::MissingArgument { cmd: "set", arg: "key" }),
        ["delete", k]  => Ok(Command::Delete { key: k.to_string() }),
        ["delete"]     => Err(CommandError::MissingArgument { cmd: "delete", arg: "key" }),
        ["quit"]       => Ok(Command::Quit),
        [cmd, ..]      => Err(CommandError::UnknownCommand { cmd: cmd.to_string() }),
    }
}
```

### The test suite

```rust
#[cfg(test)]
mod tests {
    use super::*;

    // Happy paths
    #[test]
    fn parse_get_command() {
        assert_eq!(
            parse_command("get mykey"),
            Ok(Command::Get { key: "mykey".to_string() })
        );
    }

    #[test]
    fn parse_set_command() {
        assert_eq!(
            parse_command("set foo bar"),
            Ok(Command::Set { key: "foo".to_string(), value: "bar".to_string() })
        );
    }

    #[test]
    fn parse_quit_command() {
        assert_eq!(parse_command("quit"), Ok(Command::Quit));
    }

    // Error paths
    #[test]
    fn empty_input_is_error() {
        assert_eq!(parse_command(""), Err(CommandError::Empty));
        assert_eq!(parse_command("   "), Err(CommandError::Empty));
    }

    #[test]
    fn unknown_command() {
        assert_eq!(
            parse_command("help"),
            Err(CommandError::UnknownCommand { cmd: "help".to_string() })
        );
    }

    #[test]
    fn get_missing_key() {
        assert_eq!(
            parse_command("get"),
            Err(CommandError::MissingArgument { cmd: "get", arg: "key" })
        );
    }

    #[test]
    fn set_missing_value() {
        assert_eq!(
            parse_command("set foo"),
            Err(CommandError::MissingArgument { cmd: "set", arg: "value" })
        );
    }

    // Edge cases
    #[test]
    fn extra_whitespace_is_ok() {
        assert_eq!(
            parse_command("  get   mykey  "),
            Ok(Command::Get { key: "mykey".to_string() })
        );
    }
}
```

## Applications in systems programming

### Testing a log parser

```rust
#[test]
fn parse_log_line_valid() {
    let line = "2024-01-15 10:30:00 ERROR Failed to connect to database";
    let entry = parse_log_line(line).unwrap();
    assert_eq!(entry.level, LogLevel::Error);
    assert!(entry.message.contains("database"));
}

#[test]
fn parse_log_line_unknown_level() {
    let line = "2024-01-15 10:30:00 TRACE debug info";
    assert_eq!(
        parse_log_line(line),
        Err(ParseLogError::UnknownLevel("TRACE".to_string()))
    );
}
```

### Testing a network address parser

```rust
#[test]
fn ipv4_address_parses() {
    let addr = parse_addr("192.168.1.1:8080").unwrap();
    assert_eq!(addr.port(), 8080);
}

#[test]
fn ipv6_requires_brackets() {
    assert!(parse_addr("[::1]:443").is_ok());
    assert!(parse_addr("::1:443").is_err());
}
```

## Challenges and extensions

1. **Table-driven tests**: rewrite the command parser tests as a `#[test]` that iterates over a `Vec<(&str, Result<Command, CommandError>)>`. Discuss readability tradeoffs.

2. **`proptest` introduction**: add the `proptest` crate. Write a property test asserting that `parse_command(s).is_ok()` iff `s` starts with a known command word.

3. **Async tests**: read how `#[tokio::test]` works. Write a test for the event loop from lesson 24 that asserts it processes exactly N events.

4. **Mutation testing**: conceptually: what is mutation testing? What would it catch that traditional tests miss?

## Common mistakes

1. Only testing happy paths — error paths are where the bugs live.
2. Tests that depend on iteration order (`HashMap` has no guaranteed order — sort first).
3. Mixing IO with logic so tests need real files or network connections.
4. Using `unwrap()` in tests without understanding what the Ok/Err value should be.
5. Not testing error *values* — just `is_err()` — missing field checking.

## Exercises

1. Convert one stringly-typed error in your codebase into an enum and update tests to assert exact variants.
2. Add an integration test that calls your public API end-to-end.
3. Add a regression test for a bug you encountered earlier — document what the bug was in the test name.
4. (**harder**) Write a test helper `assert_parse_ok(input, expected)` and `assert_parse_err(input, expected_err)` that produce better failure messages than raw `assert_eq!`.

## Recap

- Unit tests live next to code; integration tests live in `tests/`.
- Typed errors make failure paths precisely testable — test every variant.
- Design for testability: separate IO from pure logic.
- Test the error paths as carefully as the happy path — that's where bugs live.
- `#[should_panic(expected = "...")]` tests that the right panic fires.
