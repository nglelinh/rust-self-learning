Async in Rust is explicit: you choose a runtime, and the compiler builds state machines for you. This lesson teaches the async mental model, the basic building blocks, and how to run multiple async operations concurrently without spawning OS threads for each one.

## 60-minute teaching plan

- 0 to 10 min: When async helps (IO-bound), and when it doesn't (CPU-bound).
- 10 to 25 min: The mental model: futures, `.await`, and cooperative scheduling.
- 25 to 40 min: Tasks vs threads; why runtimes exist.
- 40 to 60 min: Mini-lab: concurrent "fetch" tool (using Tokio as the runtime).

## Learning goals

By the end of this lesson, students can:

- Explain what `async fn` returns (a future).
- Understand `.await` as a suspension point.
- Use a runtime (Tokio) to run async code.
- Run multiple async operations concurrently.

## Key concept: threads vs async tasks

| | **OS Threads** | **Async Tasks** |
|---|---|---|
| Scheduled by | OS kernel | Async runtime (user space) |
| Stack size | ~2–8 MB each | A few KB (state machine) |
| Switch overhead | Kernel context switch | Function call overhead |
| Good for | CPU-bound, parallelism | IO-bound, many concurrent ops |
| Created by | `thread::spawn` | `tokio::spawn` |
| Max practical count | Hundreds to low thousands | Millions |

**The key insight**: when waiting for IO (network, disk, timer), a thread is just sleeping — wasting memory and kernel resources. An async task yields control back to the runtime and is resumed when the IO completes. One OS thread can drive thousands of async tasks.

---

## When async is a good fit

Async shines when:

- you do lots of network or file IO
- you handle many concurrent connections (web server, proxy, client)
- you want to scale without one thread per connection

Async is **not** a magic speedup for CPU-heavy work. For CPU-bound tasks, use threads or a CPU pool. Mixing CPU-heavy work into async code blocks the executor thread and starves other tasks.

## Futures and `.await` (the mental model)

### What `async fn` returns

An `async fn` does not run immediately. It returns a value that implements the `Future` trait — a state machine that the runtime drives to completion.

```rust
async fn greet(name: &str) -> String {
    format!("Hello, {name}!")
}

// greet("Alice") returns a Future<Output = String>
// It doesn't run yet!
let fut = greet("Alice");

// To get the result, you must either .await it or give it to a runtime
let result = fut.await;
```

### What `.await` does

`.await` is a **suspension point**. When you `.await` a future:

1. If the future is ready → resume immediately with the value.
2. If the future is not ready (e.g., IO pending) → **yield control** back to the runtime.
3. The runtime schedules other ready tasks.
4. When the IO completes, the runtime wakes this task and resumes it at the `.await` point.

This is **cooperative scheduling**: tasks voluntarily yield at `.await`. A task that never `.await`s blocks the executor thread — starving all other tasks.

```rust
async fn read_two_files() -> (String, String) {
    let a = tokio::fs::read_to_string("a.txt").await;  // suspension point
    let b = tokio::fs::read_to_string("b.txt").await;  // suspension point
    (a.unwrap(), b.unwrap())
}
```

These reads are **sequential** — `b.txt` starts only after `a.txt` finishes. To read them **concurrently**, we need to compose futures.

## Tasks vs threads; why runtimes exist

In Rust, `async` requires an **executor/runtime** that:

1. Polls futures to drive them forward.
2. Manages IO event notifications (via epoll/kqueue/io_uring).
3. Provides async primitives (timers, channels, async IO).

**Tokio** is the most widely used runtime. It provides:

- An executor (thread pool for running tasks).
- Async IO wrappers (`tokio::fs`, `tokio::net`).
- Timers (`tokio::time`).
- Async primitives (`tokio::sync`).

Without a runtime, a future just sits there — no one polls it, so it never progresses.

### The entry point: `#[tokio::main]`

```rust
#[tokio::main]
async fn main() {
    println!("in async main");
}
```

This macro transforms `async fn main` into a synchronous `fn main` that creates a Tokio runtime and blocks until the top-level future completes. Internally:

```rust
fn main() {
    tokio::runtime::Builder::new_multi_thread()
        .enable_all()
        .build()
        .unwrap()
        .block_on(async_main());
}
```

## Mini-lab: concurrent fetch tool

We'll build an app that fetches multiple URLs concurrently and prints their status codes.

### Step 1: dependencies

In `Cargo.toml`:

```toml
[dependencies]
tokio  = { version = "1", features = ["macros", "rt-multi-thread", "time"] }
reqwest = { version = "0.12", default-features = true }
```

Instructor note: this repository is a Jekyll site; treat this as lecture code.

### Step 2: a single fetch

```rust
use reqwest;

async fn fetch_status(url: &str) -> Result<u16, String> {
    reqwest::get(url)
        .await
        .map_err(|e| format!("request failed: {e}"))?
        .status()
        .as_u16()
        .pipe(Ok)  // short for: let status = resp.status(); Ok(status.as_u16())
}
```

Simpler version:

```rust
async fn fetch_status(url: &str) -> Result<u16, reqwest::Error> {
    let resp = reqwest::get(url).await?;
    Ok(resp.status().as_u16())
}
```

Teaching points:

- `await?` composes: await the future, then propagate errors with `?`.
- `async fn` + `?` works just like in synchronous code.

### Step 3: sequential vs concurrent

**Sequential** (slow — waits for each URL before starting the next):

```rust
#[tokio::main]
async fn main() {
    let urls = ["https://example.com", "https://example.org"];
    for url in urls {
        match fetch_status(url).await {
            Ok(code) => println!("{url}: {code}"),
            Err(e)   => println!("{url}: error {e}"),
        }
    }
}
```

**Concurrent with `tokio::join!`** (fast — all fetches run simultaneously):

```rust
use tokio::join;

#[tokio::main]
async fn main() {
    let (r1, r2) = join!(
        fetch_status("https://example.com"),
        fetch_status("https://example.org"),
    );
    println!("example.com: {:?}", r1);
    println!("example.org: {:?}", r2);
}
```

`join!` polls all futures concurrently and returns when **all** complete. Total time ≈ slowest URL (not sum of all URLs).

### Step 4: dynamic list with `futures::future::join_all`

```rust
use futures::future::join_all;

async fn fetch_all(urls: &[&str]) -> Vec<(&str, Result<u16, reqwest::Error>)> {
    let futures: Vec<_> = urls.iter()
        .map(|&url| async move { (url, fetch_status(url).await) })
        .collect();
    join_all(futures).await
}

#[tokio::main]
async fn main() {
    let urls = ["https://example.com", "https://example.org", "https://rust-lang.org"];
    for (url, result) in fetch_all(&urls).await {
        match result {
            Ok(code) => println!("{url}: {code}"),
            Err(e)   => println!("{url}: ERROR {e}"),
        }
    }
}
```

### Step 5: add timeouts

Every network call in production needs a timeout:

```rust
use tokio::time::{timeout, Duration};

async fn fetch_with_timeout(url: &str, secs: u64) -> Result<u16, String> {
    match timeout(Duration::from_secs(secs), fetch_status(url)).await {
        Ok(Ok(code))   => Ok(code),
        Ok(Err(e))     => Err(format!("request error: {e}")),
        Err(_elapsed)  => Err("timed out".to_string()),
    }
}
```

Teaching points:

- `timeout(duration, future)` is itself a future.
- Returns `Ok(inner_result)` if the inner future completed in time.
- Returns `Err(Elapsed)` if the timeout fired first.
- Always wrap external calls with timeouts in production systems.

## Code walkthrough: naive → idiomatic

### Naive: blocking code in async context

```rust
// This blocks the executor thread!
async fn read_file_blocking(path: &str) -> String {
    std::fs::read_to_string(path).unwrap()  // synchronous IO
}
```

While `read_to_string` blocks, the executor thread can't run other tasks.

### Idiomatic: use async IO

```rust
async fn read_file_async(path: &str) -> String {
    tokio::fs::read_to_string(path).await.unwrap()  // yields while IO is in flight
}
```

Or use `tokio::task::spawn_blocking` for unavoidable blocking work:

```rust
async fn compute_hash(data: Vec<u8>) -> [u8; 32] {
    tokio::task::spawn_blocking(move || {
        sha256_hash(&data)  // CPU-heavy — run in a thread pool
    }).await.unwrap()
}
```

## Applications in systems programming

### High-concurrency HTTP client

A CI system that checks 500 GitHub repositories simultaneously:

```rust
let futures: Vec<_> = repos.iter()
    .map(|repo| check_status(repo))
    .collect();
let results = join_all(futures).await;
```

With threads, 500 repos = 500 threads = ~500 MB of stack. With async tasks, 500 repos = 500 state machines = ~500 KB.

### Async DNS resolver

Network tools like DNS resolvers need to fire many queries simultaneously and collect responses as they arrive — perfect for async.

### Event-driven game server

A game server handling thousands of player connections: each player's connection is an async task. The server dispatches game events, timers, and IO concurrently without threads for each player.

## Challenges and extensions

1. **`tokio::spawn`**: use `tokio::spawn` to run each fetch in a separate Tokio task. How does this differ from `join!`? (Hint: tasks can run on different OS threads in the thread pool.)

2. **`select!`**: replace `join!` with `tokio::select!` — return the result of whichever URL responds first.

3. **Retry with backoff**: implement exponential backoff: if a fetch fails, retry after 100ms, 200ms, 400ms before giving up.

4. **Streaming results**: instead of waiting for all fetches to complete, print results as they arrive using `FuturesUnordered`.

5. **Cancellation**: use a `CancellationToken` from the `tokio-util` crate to cancel all pending fetches if the first one fails.

---

## Common mistakes

1. **Blocking IO in async code**: using `std::fs`, `std::net`, or CPU-heavy code blocks the executor thread. Use `tokio::fs`, `tokio::net`, or `spawn_blocking`.
2. **Holding a `std::sync::Mutex` across `.await`**: the mutex is held while suspended — other tasks can't lock it. Use `tokio::sync::Mutex` instead, or drop the guard before `.await`.
3. **Assuming async = fast**: async has overhead compared to synchronous code for single operations. The win is concurrency at scale, not per-operation speed.
4. **Forgetting to run async functions**: calling `fetch_status(url)` without `.await` returns a future but never runs it.

## Recap

- `async fn` returns a future; `.await` suspends until the future is ready.
- A runtime (Tokio) polls futures — without one, they never run.
- Concurrency in async: compose futures with `join!`, `join_all`, or `tokio::spawn`.
- Never block the executor thread with synchronous IO or CPU-heavy work.
- Every network call needs a timeout.
