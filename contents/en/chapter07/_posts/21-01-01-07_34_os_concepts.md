Before building a desktop chat application, you need to understand what the operating system provides and what it demands. This lesson maps the OS concepts that directly shape how a GPUI application is structured: the process model, memory, the event loop, the file system, and timers. None of this requires kernel internals — you need the conceptual model that makes your design decisions obvious.

## 60-minute teaching plan

- 0 to 10 min: Processes and threads — what your app actually is at the OS level.
- 10 to 20 min: Memory model — stack, heap, and why Rust's ownership rules exist.
- 20 to 35 min: The event loop — the pattern behind every UI framework.
- 35 to 45 min: File system basics — reading config, persisting history.
- 45 to 55 min: Timers and scheduling — precision, OS jitter, and practical use.
- 55 to 60 min: How these concepts appear in GPUI; recap.

## Learning goals

By the end of this lesson, students can:

- Explain the difference between a process and a thread, and why the UI thread must stay free.
- Describe stack vs heap allocation in the context of a Rust GUI app.
- Trace the event loop pattern inside GPUI's runtime.
- Read and write files safely from a Rust desktop application.
- Use timers for periodic work without blocking the UI.

## Processes vs threads

### What a process is

When your compiled binary starts, the operating system creates a **process**: an isolated unit with its own virtual address space, file descriptor table, and at least one thread. Your entire chat application runs inside one process.

```
┌─────────────────────────────────┐
│          Your OS Process         │
│                                 │
│  ┌─────────┐  ┌─────────────┐  │
│  │ UI Thread│  │ Network Task│  │
│  │ (main)  │  │  (async)    │  │
│  └─────────┘  └─────────────┘  │
│                                 │
│  ┌──────────────────────────┐   │
│  │      Shared Heap         │   │
│  └──────────────────────────┘   │
└─────────────────────────────────┘
```

Processes are isolated from each other — a crash in a different process won't take your app down. This is why some applications (browsers, Zed) spin off separate processes for plugins or rendering.

### What a thread is

A **thread** is an independent sequence of instructions that the OS scheduler runs. All threads inside one process share the same memory — they can read and write the same data, which is both powerful and dangerous (this is where data races come from).

Your application has at minimum:

- **UI thread**: the main thread, runs the event loop, must never block.
- **Async executor threads**: Tokio's worker threads for network I/O, file I/O, and timers.
- **Potentially**: OS-level render threads that GPUI manages internally on Metal/Vulkan.

### The cardinal rule of desktop development

> **Never block the UI thread.**

If the UI thread blocks — waiting on a network response, sleeping, spinning on a lock — the app freezes. The user sees an unresponsive window. On macOS the spinning beach ball appears. On Linux the window compositor may kill the window.

```rust
// WRONG — blocks the UI thread for however long the HTTP request takes
impl Render for ChatView {
    fn render(&mut self, cx: &mut ViewContext<Self>) -> impl IntoElement {
        let response = reqwest::blocking::get("https://api.example.com/messages").unwrap();
        // ...
    }
}

// CORRECT — fire async work from the view; handle the result when it arrives
impl ChatView {
    fn load_messages(&mut self, cx: &mut ViewContext<Self>) {
        cx.spawn(|view, mut cx| async move {
            let response = reqwest::get("https://api.example.com/messages").await;
            cx.update_view(&view, |this, cx| {
                this.messages = parse_response(response);
                cx.notify();
            }).ok();
        }).detach();
    }
}
```

### Threads vs async tasks

| | OS thread | Async task |
|---|---|---|
| Cost | ~8MB stack, kernel object | ~few KB |
| Switches | OS scheduler (preemptive) | Explicit `.await` points |
| Good for | CPU-bound, blocking work | I/O-bound, many concurrent operations |
| In Tokio | `tokio::task::spawn_blocking` | `tokio::spawn` |

For a chat app, almost everything is I/O-bound (network, disk). Async tasks are the right tool. The only case for a real thread is CPU-heavy work like message encryption or search indexing.

## Memory: stack vs heap

### Stack allocation

The stack is a LIFO (last-in, first-out) region of memory managed automatically. Every function call pushes a stack frame containing local variables; when the function returns, the frame is popped.

```rust
fn process_message(msg: &str) -> usize {
    let count = msg.len();    // count lives on the stack
    let trimmed = msg.trim(); // a slice — pointer + length, also on the stack
    count
}   // count and trimmed are gone here — no allocation to free
```

Stack allocation is essentially free and very cache-friendly. The constraint: you must know the size at compile time.

### Heap allocation

The heap is a large pool of memory that can be allocated and freed at runtime in arbitrary order. In Rust, heap allocation happens through `Box`, `Vec`, `String`, `Arc`, etc.

```rust
// Vec<Message> lives on the heap — size not known at compile time
let messages: Vec<Message> = load_from_disk()?;

// Arc puts the data on the heap and reference-counts it
// so multiple components can share the same message list
let shared = Arc::new(messages);
```

### Why this matters for a chat app

- **Message list**: potentially thousands of entries. Always heap-allocated (`Vec<Message>`).
- **Message content**: strings of variable length. Heap-allocated (`String`).
- **Shared state between UI and network task**: wrap in `Arc<Mutex<T>>` or use `Model<T>` (GPUI's entity system, which manages the heap allocation for you).
- **Avoid unnecessary clones**: clone a `String` (heap allocation) only when you must transfer ownership. Pass `&str` (a stack-resident borrow) for read-only access.

```rust
// WRONG — clones every message string on every render pass
fn render_preview(msg: &Message) -> String {
    msg.content.clone().truncate(100); // also wrong: truncate returns ()
    msg.content.clone()[..100.min(msg.content.len())].to_string()
}

// CORRECT — borrows the string, no allocation
fn render_preview(msg: &Message) -> &str {
    let end = 100.min(msg.content.len());
    &msg.content[..end]
}
```

## The event loop

### The pattern

Every UI framework is built around an event loop. Conceptually:

```
loop {
    event = wait_for_next_event();
    match event {
        Event::MouseClick(pos)   => handle_click(pos),
        Event::KeyPress(key)     => handle_key(key),
        Event::NetworkMessage(m) => handle_message(m),
        Event::TimerTick(id)     => handle_timer(id),
        Event::Quit              => break,
    }
    if state_changed {
        render();
    }
}
```

This is not hypothetical — it's the actual structure inside frameworks like GPUI, Qt, GTK, and Win32. The loop blocks on the "wait" call (so it uses no CPU when idle) and wakes up exactly when something needs attention.

### Events in a chat app

Your chat application receives these event categories:

| Source | Events |
|--------|--------|
| OS input | Mouse clicks, key presses, window resize, focus/blur |
| Network | New message received, connection established, connection lost |
| Timers | Reconnect retry delay, polling heartbeat, notification timeout |
| App internal | User sends a message (triggers a network write) |

### How GPUI's event loop works

GPUI wraps the platform's native event loop (on macOS: `NSRunLoop` / `CFRunLoop`). You don't write the loop yourself — GPUI calls your `render` function when the view is invalidated, and calls your event handlers when events fire.

```rust
// GPUI calls this when the user clicks and you've registered an on_click handler
div()
    .on_click(cx.listener(|this, _event, cx| {
        // You are inside the event loop here, on the UI thread
        // Do NOT block — only synchronous state updates are allowed
        this.send_message(cx);
    }))
```

For anything that takes time — network calls, file reads, database queries — hand the work to an async task:

```rust
fn send_message(&mut self, cx: &mut ViewContext<Self>) {
    let content = self.input.take();
    cx.spawn(|view, mut cx| async move {
        // This runs on Tokio's thread pool, not the UI thread
        network_send(content).await;
        cx.update_view(&view, |this, cx| {
            this.pending = false;
            cx.notify();
        }).ok();
    }).detach();
}
```

### What "non-blocking" means precisely

A function is non-blocking if it returns to the caller almost immediately — it does not wait for I/O to complete, it does not sleep, and it does not spin in a loop. The rule is:

- Synchronous CPU work under ~1ms: acceptable on the UI thread.
- Anything involving I/O, network, or sleep: move to an async task.

## File system basics

### Why a chat app needs the file system

| Use case | What to read/write |
|----------|-------------------|
| Chat history persistence | Append messages to a local file or SQLite |
| Configuration | User settings: server URL, display name, theme |
| Logging | Diagnostic output for debugging |
| Attachments | Images and files sent in chat |
| Auth tokens | Saved login credentials (needs secure storage) |

### Reading a file

```rust
use std::fs;
use std::path::PathBuf;

fn load_config(config_dir: &PathBuf) -> Result<AppConfig, ConfigError> {
    let path = config_dir.join("chat.toml");
    let text = fs::read_to_string(&path)
        .map_err(|e| ConfigError::ReadFailed { path: path.clone(), source: e })?;
    toml::from_str(&text)
        .map_err(|e| ConfigError::ParseFailed { path, source: e })
}
```

### Writing a file atomically

Never write directly to the target file — if the process crashes mid-write, you get a corrupt file. Write to a temp file, then rename:

```rust
use std::fs;

fn save_config(config: &AppConfig, path: &std::path::Path) -> std::io::Result<()> {
    let tmp = path.with_extension("toml.tmp");
    let text = toml::to_string_pretty(config).expect("serialization is infallible");
    fs::write(&tmp, text)?;
    fs::rename(&tmp, path)?; // atomic on most filesystems
    Ok(())
}
```

### Platform config directories

Use the `dirs` crate to find the right location per OS:

```toml
[dependencies]
dirs = "5"
```

```rust
fn config_dir() -> PathBuf {
    dirs::config_dir()
        .unwrap_or_else(|| PathBuf::from("."))
        .join("my-chat-app")
}
```

| OS | `dirs::config_dir()` |
|----|----------------------|
| macOS | `~/Library/Application Support` |
| Linux | `~/.config` |
| Windows | `%APPDATA%` |

### File I/O in an async context

`std::fs` functions are synchronous — they block the calling thread. Never call them directly from async code running on the UI thread. Use `tokio::fs` instead:

```rust
use tokio::fs;

async fn load_history(path: &std::path::Path) -> std::io::Result<Vec<Message>> {
    let bytes = fs::read(path).await?;   // non-blocking read
    Ok(serde_json::from_slice(&bytes)?)
}
```

Or, for truly heavy file work, use `tokio::task::spawn_blocking` to run synchronous code on a dedicated thread pool without blocking async workers.

## Timers and scheduling

### OS scheduling is not perfectly precise

Your timer fires "at least N milliseconds from now" — not "exactly N milliseconds from now." The OS scheduler decides when your thread gets CPU time. A 100ms timer might fire at 102ms, 105ms, or later under heavy load. This is normal and expected.

**Consequences for chat apps**:
- Don't use timers for cryptographic randomness or sub-millisecond precision.
- Heartbeat pings and reconnect retries tolerate ±50ms jitter without issue.
- UI animation timers should use the display refresh callback (GPUI handles this internally).

### Creating a recurring timer in a GPUI context

```rust
use std::time::Duration;

impl ChatView {
    fn start_heartbeat(&self, cx: &mut ViewContext<Self>) {
        cx.spawn(|view, mut cx| async move {
            let mut interval = tokio::time::interval(Duration::from_secs(30));
            loop {
                interval.tick().await;           // waits ~30 seconds
                cx.update_view(&view, |this, cx| {
                    this.send_heartbeat(cx);
                }).ok();
            }
        }).detach();
    }
}
```

`tokio::time::interval` uses the OS timer facility under the hood. It "ticks" at the requested interval without blocking any thread.

### One-shot delay

```rust
async fn reconnect_after_delay(delay: Duration) {
    tokio::time::sleep(delay).await;
    // reconnect logic here
}
```

### Exponential backoff for reconnect

```rust
async fn connect_with_retry(url: &str) -> Result<WsStream, ConnectError> {
    let mut delay = Duration::from_millis(500);
    for attempt in 0..8 {
        match ws_connect(url).await {
            Ok(stream) => return Ok(stream),
            Err(e) if attempt < 7 => {
                eprintln!("connect failed, retry in {:?}: {e}", delay);
                tokio::time::sleep(delay).await;
                delay = (delay * 2).min(Duration::from_secs(60));
            }
            Err(e) => return Err(e),
        }
    }
    unreachable!()
}
```

The delay doubles on each failure, capped at 60 seconds. This avoids hammering a server that's down.

## How these concepts appear in GPUI

| OS concept | GPUI counterpart |
|------------|-----------------|
| Process | Your binary — `App::new().run(...)` |
| UI thread | The thread `run` executes on — never block |
| Event loop | GPUI's internal run loop — you hook in via `Render` and listeners |
| Heap allocation | `Model<T>` — framework-managed entity heap |
| Timer | `cx.spawn` + `tokio::time::interval` |
| File I/O | `cx.spawn` + `tokio::fs` |
| Thread pool | Tokio's worker threads, accessed via `cx.spawn` or `spawn_blocking` |

You won't write `loop { wait_for_event(); ... }` by hand — GPUI does that. But understanding what it's doing makes it obvious why the rules exist: never block, always use `cx.spawn` for slow work, never call `cx.notify()` from a background thread without `cx.update_view`.

## Common mistakes

1. **Calling `std::fs::read_to_string` inside an async task on Tokio's default executor** — it blocks the worker thread, starving other tasks. Use `tokio::fs` or `spawn_blocking`.

2. **Assuming timers are precise** — add ±10–50ms tolerance to any timer-dependent logic.

3. **Blocking inside `render`** — `render` is called on the UI thread. Any blocking call here freezes the entire window.

4. **Storing large buffers on the stack** — large `[u8; 65536]` arrays on the stack can overflow it. Use `Vec<u8>` for large buffers.

5. **Shared mutable state without synchronization** — if you must share data between the UI and a background task, use `Arc<Mutex<T>>` or GPUI's `Model<T>` entity system. Never use raw shared state.

## Recap

- A process is your app instance; threads are execution units inside it. The UI thread must never block.
- Stack memory is free and scoped to function calls. Heap memory (`Vec`, `String`, `Arc`) is dynamically sized and managed by Rust's ownership system.
- The event loop is the core pattern: wait for an event, handle it, update state, render. GPUI wraps this for you.
- Use `tokio::fs` for async file I/O. Use atomic rename for safe writes.
- OS timers are approximate. Use `tokio::time::interval` for recurring work inside `cx.spawn`.
- These concepts dictate the architecture: anything slow goes in an async task, results come back via `cx.update_view`.
