A desktop chat application is a network application. It connects to a server, exchanges messages in real time, and must handle unreliable connections gracefully. This lesson covers the networking concepts that underpin every chat system: TCP, WebSocket, HTTP vs persistent connections, message serialization, and the full connection lifecycle from first connect to graceful shutdown.

## 60-minute teaching plan

- 0 to 10 min: Client–server model — what your app is and what the server is.
- 10 to 20 min: TCP — reliability, ordering, and connection state.
- 20 to 35 min: WebSocket — why chat uses it, how it works on top of TCP.
- 35 to 45 min: HTTP vs WebSocket — when to use each.
- 45 to 55 min: Serialization with Serde — JSON and binary formats.
- 55 to 60 min: Connection lifecycle and recap.

## Learning goals

By the end of this lesson, students can:

- Explain the client–server model and where a desktop chat app fits.
- Describe what TCP guarantees and why those guarantees matter for chat.
- Explain what WebSocket adds on top of TCP and why it is the standard for real-time chat.
- Serialize and deserialize chat messages using Serde.
- Handle the full connection lifecycle: connect, send, receive, reconnect, shutdown.

## The client–server model

### What your app is

Your desktop chat application is a **client**: it initiates connections to a server, sends requests, and receives responses. It does not listen for incoming connections from the internet.

```
┌─────────────┐    WebSocket     ┌─────────────────┐
│  Desktop App │◄────────────────►│   Chat Server    │
│   (Client)  │                  │   (Server)       │
└─────────────┘                  └────────┬─────────┘
                                          │
                              ┌───────────┴──────────┐
                              │  Other Clients (users) │
                              └───────────────────────┘
```

The server's job: receive messages from one client and broadcast them to the others. Your app's job: connect, authenticate, send what the user types, and display what arrives.

### What you control vs what the server controls

| Your client controls | Server controls |
|---------------------|-----------------|
| When to connect | Authentication logic |
| What messages to send | Message routing |
| How to display received data | Message persistence |
| Reconnect behavior | Rate limiting |
| Local message history | Message ordering across clients |

Understanding this boundary prevents over-engineering the client and under-specifying the server contract.

## TCP: the foundation

### What TCP is

**TCP (Transmission Control Protocol)** is the transport layer protocol that chat systems rely on. It provides three guarantees that make it suitable for chat:

1. **Reliable delivery**: lost packets are automatically retransmitted. You don't implement this.
2. **Ordered delivery**: bytes arrive in the order they were sent. Message 1 always arrives before message 2.
3. **Connection-based**: there is an explicit handshake to open a connection and a handshake to close it.

These guarantees come at a cost: TCP has overhead (handshakes, acknowledgements, retransmits). For chat — where correctness matters more than latency below 10ms — that cost is entirely acceptable.

### What TCP does NOT provide

- **Message boundaries**: TCP is a byte stream. If you send two 100-byte messages, the receiver might get 200 bytes at once, or 50 bytes then 150 bytes. Your application protocol must define where one message ends and the next begins. WebSocket handles this for you.
- **Encryption**: TCP sends bytes in plaintext. TLS (the `s` in `wss://`) wraps TCP and provides encryption.
- **Application-level semantics**: TCP delivers bytes. It has no concept of "a chat message" or "a typing indicator."

### TCP in Rust

You rarely use TCP directly. The `tokio::net::TcpStream` type exposes raw TCP, but in practice you use a higher-level protocol (WebSocket) built on top of it.

```rust
// Low-level TCP — you won't usually write this for chat
use tokio::net::TcpStream;
use tokio::io::{AsyncReadExt, AsyncWriteExt};

let mut stream = TcpStream::connect("chat.example.com:8080").await?;
stream.write_all(b"hello").await?;

let mut buf = vec![0u8; 1024];
let n = stream.read(&mut buf).await?;
println!("received: {:?}", &buf[..n]);
```

## WebSocket: the right tool for chat

### What WebSocket adds

WebSocket is a protocol built on top of TCP that solves the problems TCP leaves open:

- **Message boundaries**: a WebSocket frame carries its own length. You receive complete messages, not byte streams.
- **Full-duplex**: both sides can send at any time, without a request/response cycle.
- **Persistent connection**: the connection stays open for the entire chat session. No reconnect per message.
- **Ping/pong frames**: built-in heartbeat mechanism to detect dead connections.

### How WebSocket starts

WebSocket begins as an HTTP upgrade request:

```
Client → Server:
GET /ws HTTP/1.1
Host: chat.example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13

Server → Client:
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
```

After the `101` response, the TCP connection stays open and both sides switch to the WebSocket frame format. HTTP is gone — the connection is now purely WebSocket.

### Real-time chat events over WebSocket

```
User types: "Hello"
    ↓
Client sends WebSocket frame:
  {"type": "message", "content": "Hello", "room": "general"}
    ↓
Server receives, validates, stores
    ↓
Server broadcasts to all connected clients:
  {"type": "message", "from": "alice", "content": "Hello", "ts": 1714600000}
    ↓
All clients receive the frame and update their UI
```

This all happens in ~50–150ms over a good connection. There is no polling, no repeated HTTP requests.

### WebSocket in Rust

Use the `tokio-tungstenite` crate:

```toml
[dependencies]
tokio-tungstenite = { version = "0.21", features = ["native-tls"] }
futures-util = "0.3"
```

#### Connecting

```rust
use tokio_tungstenite::{connect_async, tungstenite::Message};
use futures_util::{SinkExt, StreamExt};

async fn connect(url: &str) -> anyhow::Result<()> {
    let (ws_stream, _response) = connect_async(url).await?;
    let (mut write, mut read) = ws_stream.split();

    // Send a message
    let msg = serde_json::json!({
        "type": "join",
        "room": "general"
    });
    write.send(Message::Text(msg.to_string())).await?;

    // Receive messages
    while let Some(msg) = read.next().await {
        match msg? {
            Message::Text(text) => {
                println!("received: {text}");
            }
            Message::Close(_) => {
                println!("server closed connection");
                break;
            }
            _ => {} // ping/pong handled by tungstenite automatically
        }
    }
    Ok(())
}
```

#### Splitting the stream for concurrent send and receive

In a real app, you need to send messages (triggered by user actions) and receive messages (arriving from the server) concurrently. Split the stream:

```rust
use tokio::sync::mpsc;

async fn run_ws(url: &str, mut outgoing: mpsc::Receiver<String>) -> anyhow::Result<()> {
    let (ws_stream, _) = connect_async(url).await?;
    let (mut write, mut read) = ws_stream.split();

    loop {
        tokio::select! {
            // Something arrived from the server
            Some(msg) = read.next() => {
                if let Ok(Message::Text(text)) = msg {
                    handle_incoming(text);
                }
            }
            // User wants to send something
            Some(text) = outgoing.recv() => {
                write.send(Message::Text(text)).await?;
            }
        }
    }
}
```

`tokio::select!` races the two async operations — whichever has data ready first runs. This is the idiomatic pattern for a network loop that must both read and write.

## HTTP vs WebSocket: choosing the right tool

| | HTTP (request/response) | WebSocket (persistent) |
|---|---|---|
| Connection | New connection per request (HTTP/1.1) or multiplexed (HTTP/2) | One connection for the session |
| Direction | Client initiates every exchange | Either side can initiate |
| State | Stateless | Stateful |
| Latency | Higher (handshake per request) | Lower (connection already open) |
| Use for | User auth, profile fetch, file upload | Chat messages, typing indicators, presence |
| Rust crate | `reqwest` | `tokio-tungstenite` |

### In a chat app, you use both

```rust
// HTTP for one-off operations
let profile = reqwest::get(&format!("{base}/users/{id}")).await?
    .json::<UserProfile>().await?;

// WebSocket for the real-time stream
let (ws, _) = connect_async(&format!("{base_ws}/chat")).await?;
```

The HTTP calls are short-lived and infrequent. The WebSocket connection persists for the duration of the session.

## Serialization with Serde

### Why serialization matters

Your Rust structs cannot travel over the network as-is. They must be converted to bytes (serialized), transmitted, received, and converted back (deserialized). Serde is the Rust ecosystem's serialization framework.

```toml
[dependencies]
serde = { version = "1", features = ["derive"] }
serde_json = "1"
```

### Defining a message type

```rust
use serde::{Deserialize, Serialize};
use chrono::{DateTime, Utc};

#[derive(Debug, Clone, Serialize, Deserialize)]
#[serde(tag = "type", rename_all = "snake_case")]
pub enum ClientMessage {
    Join   { room: String },
    Leave  { room: String },
    Send   { room: String, content: String },
    Ping,
}

#[derive(Debug, Clone, Serialize, Deserialize)]
#[serde(tag = "type", rename_all = "snake_case")]
pub enum ServerMessage {
    Message {
        id:      String,
        from:    String,
        room:    String,
        content: String,
        ts:      DateTime<Utc>,
    },
    UserJoined { user: String, room: String },
    UserLeft   { user: String, room: String },
    Error      { code: u32, message: String },
    Pong,
}
```

Using `#[serde(tag = "type")]` makes the JSON include a `"type"` field that discriminates the variant — this is the standard pattern for WebSocket protocol messages.

### Serializing and deserializing

```rust
// Outgoing: Rust → JSON → WebSocket frame
let msg = ClientMessage::Send {
    room: "general".into(),
    content: "Hello, world!".into(),
};
let text = serde_json::to_string(&msg)?;
// → {"type":"send","room":"general","content":"Hello, world!"}
write.send(Message::Text(text)).await?;

// Incoming: WebSocket frame → JSON → Rust
if let Message::Text(text) = raw_msg {
    match serde_json::from_str::<ServerMessage>(&text) {
        Ok(ServerMessage::Message { from, content, ts, .. }) => {
            display_message(from, content, ts);
        }
        Ok(ServerMessage::Error { code, message }) => {
            eprintln!("server error {code}: {message}");
        }
        Ok(_) => {} // other variants
        Err(e) => {
            eprintln!("malformed message: {e} — raw: {text}");
        }
    }
}
```

### JSON vs binary

| | JSON | Binary (MessagePack, bincode) |
|---|---|---|
| Human-readable | Yes | No |
| Size | Larger | Smaller |
| Parse speed | Slower | Faster |
| Debugging | Easy — can print frames | Hard without a decoder |
| Use for | Chat apps, most apps | High-throughput, low-latency systems |

Start with JSON. Switch to MessagePack (`rmp-serde`) only if profiling shows serialization as a bottleneck — for a chat app, it almost never will be.

## Connection lifecycle

A WebSocket connection is not a fire-and-forget. It has a lifecycle you must manage.

### States

```
DISCONNECTED
    │
    │  connect_async()
    ▼
CONNECTING ────── error ──► DISCONNECTED (retry)
    │
    │  101 Switching Protocols
    ▼
CONNECTED ─────── network error ──► DISCONNECTED (retry)
    │
    │  user quits / server sends Close frame
    ▼
CLOSED
```

### Connect with retry

```rust
pub struct WsClient {
    url:   String,
    state: ConnectionState,
}

#[derive(Debug, Clone, PartialEq)]
pub enum ConnectionState {
    Disconnected,
    Connecting,
    Connected,
    Closed,
}

impl WsClient {
    pub async fn connect_with_retry(&mut self) -> anyhow::Result<WsStream> {
        let mut delay = Duration::from_millis(500);
        self.state = ConnectionState::Connecting;

        for attempt in 1..=8 {
            match connect_async(&self.url).await {
                Ok((stream, _)) => {
                    self.state = ConnectionState::Connected;
                    return Ok(stream);
                }
                Err(e) => {
                    eprintln!("attempt {attempt} failed: {e}");
                    if attempt < 8 {
                        tokio::time::sleep(delay).await;
                        delay = (delay * 2).min(Duration::from_secs(30));
                    }
                }
            }
        }
        self.state = ConnectionState::Disconnected;
        anyhow::bail!("failed to connect after 8 attempts")
    }
}
```

### Detecting a dead connection: heartbeats

TCP does not detect a silently broken connection quickly. A client behind a NAT or a proxy might lose connectivity, but the TCP connection stays open (from each side's perspective) for minutes. Use ping/pong to detect this:

```rust
async fn run_with_heartbeat(
    mut write: WsSink,
    mut read: WsStream,
) -> anyhow::Result<()> {
    let mut ping_interval = tokio::time::interval(Duration::from_secs(30));
    let mut last_pong = std::time::Instant::now();

    loop {
        tokio::select! {
            _ = ping_interval.tick() => {
                if last_pong.elapsed() > Duration::from_secs(90) {
                    anyhow::bail!("server stopped responding to pings");
                }
                write.send(Message::Ping(vec![])).await?;
            }
            Some(msg) = read.next() => {
                match msg? {
                    Message::Pong(_) => { last_pong = std::time::Instant::now(); }
                    Message::Text(t) => { handle_message(t); }
                    Message::Close(_) => break,
                    _ => {}
                }
            }
        }
    }
    Ok(())
}
```

### Graceful shutdown

When the user quits, send a WebSocket Close frame and wait for the server's Close response:

```rust
async fn shutdown(mut write: WsSink, mut read: WsStream) {
    // Signal intent to close
    let _ = write.send(Message::Close(None)).await;

    // Drain remaining frames (server may send one more Close)
    tokio::time::timeout(Duration::from_secs(3), async {
        while let Some(Ok(msg)) = read.next().await {
            if matches!(msg, Message::Close(_)) { break; }
        }
    }).await.ok();
}
```

## Message flow: end to end

Here is the complete path a chat message takes:

```
1. User types "Hello" and presses Enter
   → UI thread: on_click / on_key_press handler fires
   → State update: pending message added to local list
   → cx.notify() — UI re-renders with message in "sending" state

2. Background task: serialize and send
   → ClientMessage::Send { room, content } → JSON string
   → WebSocket write.send(Message::Text(json)).await

3. Server receives, validates, assigns ID and timestamp
   → Stores in database
   → Broadcasts to all clients in the room

4. Your client receives the broadcast
   → WebSocket read.next() fires
   → Deserialize to ServerMessage::Message { id, from, content, ts }
   → Channel sends the message to GPUI model

5. GPUI model receives message
   → Appends to messages Vec
   → cx.notify() — UI re-renders with confirmed message
```

The "pending → confirmed" transition (steps 1→5) matters: show the message immediately (optimistic UI), then replace the pending state with the server-confirmed version. This makes the UI feel instant even on slow connections.

## In-class exercises

1. Connect to a public WebSocket echo server (e.g., `wss://echo.websocket.org`) using `tokio-tungstenite`. Send your name and print what comes back.

2. Define `ClientMessage` and `ServerMessage` enums for a minimal chat protocol. Write unit tests that round-trip each variant through `serde_json`: `serialize → to_string → from_str → deserialize`. Assert equality.

3. Implement `connect_with_retry` with exponential backoff (cap at 30 seconds). Simulate failures by connecting to `ws://127.0.0.1:9999` (nothing listening there). Observe the backoff delays in your logs.

4. Build a minimal WebSocket read/write loop with `tokio::select!`. The loop should handle incoming text frames (print them) and a `tokio::sync::mpsc::Receiver<String>` for outgoing messages (send them). Test with the echo server.

5. Add a heartbeat: send a Ping every 15 seconds. Track the last Pong time. If no Pong arrives within 45 seconds, log "connection dead" and break the loop.

## Common mistakes

1. **Forgetting that TCP is a byte stream** — if you build on raw TCP, you must frame your messages. Use WebSocket; it does this for you.

2. **Not handling disconnection** — assume the connection will drop. The reconnect logic is not optional for a production chat app.

3. **Serializing in the UI thread** — for very large payloads, `serde_json::to_string` can take meaningful time. Prefer to serialize in the async task, not in the `on_click` handler.

4. **No timeout on `read.next()`** — if the server goes silent without sending a Close frame, `read.next()` will hang forever. Add a heartbeat and timeout.

5. **Trusting incoming data** — always parse with `serde_json::from_str::<ServerMessage>` and handle `Err`. Never `unwrap()` incoming network data.

6. **Not draining the read side on shutdown** — sending a Close frame and immediately dropping the stream may leave the server with an error. Drain for a few seconds.

## Recap

- Your desktop app is a WebSocket client connecting to a chat server. The server handles routing and persistence.
- TCP provides reliable ordered byte delivery. WebSocket adds message framing and full-duplex on top of TCP.
- Use HTTP (`reqwest`) for one-off operations (auth, profile fetch) and WebSocket (`tokio-tungstenite`) for the real-time message stream.
- Define message types as Rust enums and use Serde for JSON serialization. Use `#[serde(tag = "type")]` to discriminate variants.
- Manage the full connection lifecycle: connect with exponential backoff retry, send heartbeat pings, detect dead connections, and close gracefully.
- Use `tokio::select!` to concurrently read incoming frames and send outgoing messages from the same connection.
