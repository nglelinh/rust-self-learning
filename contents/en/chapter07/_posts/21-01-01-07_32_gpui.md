GPUI is the UI framework that powers the Zed code editor. It renders everything on the GPU, manages state through an entity system, and blends the ergonomics of immediate-mode authoring with the efficiency of a retained element tree. This lesson teaches the framework's core concepts and builds a working app.

> **Maturity note**: The standalone `gpui` crate is still being stabilized for use outside Zed. APIs may change between versions. macOS has the most complete support; Linux and Windows are available but less polished. Treat this lesson as a deep-dive into an emerging framework, not a stable production recommendation.

## 60-minute teaching plan

## Learning goals

By the end of this lesson, students can:

- Bootstrap a GPUI application and open a window.
- Implement the `Render` trait to define UI as an element tree.
- Manage state in a `Model<T>` entity and subscribe a view to model changes.
- Use the fluent element API for layout and basic styling.
- Explain where GPUI fits relative to egui and iced.

## Why GPUI?

The Zed team needed a UI framework that could:

1. Render a code editor with millions of characters without frame drops.
2. Support GPU-accelerated custom drawing (syntax highlighting, minimap, inline AI diffs).
3. Work in a highly concurrent Rust codebase with many async tasks modifying state.
4. Feel productive for the developers building Zed features daily.

No existing Rust framework met all four constraints, so they built GPUI. The result is a framework where the rendering path is always on the GPU (Metal/Vulkan/DirectX), state changes are propagated through an explicit entity graph, and the UI authoring style is close enough to immediate-mode to feel natural.

## Core primitives

### App and AppContext

`App` is the entry point. You create one per process and call `.run()` with a closure that receives an `AppContext`:

```rust
use gpui::*;

fn main() {
    App::new().run(|cx: &mut AppContext| {
        // everything starts here
    });
}
```

`AppContext` (`cx`) is your handle to the GPUI runtime. You use it to open windows, create models, and read/write global state.

### Window

Open a window from inside the `run` closure:

```rust
App::new().run(|cx: &mut AppContext| {
    cx.open_window(
        WindowOptions {
            window_bounds: Some(WindowBounds::Windowed(Bounds {
                origin: point(px(0.0), px(0.0)),
                size: size(px(800.0), px(600.0)),
            })),
            ..Default::default()
        },
        |cx| cx.new_view(|_cx| HelloView),
    ).unwrap();
});
```

`cx.open_window` takes options and a closure that returns the root `View`. A view is the unit of rendering in GPUI.

### View and the Render trait

A view is any struct that implements `Render`. The `render` method returns an element tree:

```rust
struct HelloView;

impl Render for HelloView {
    fn render(&mut self, _cx: &mut ViewContext<Self>) -> impl IntoElement {
        div()
            .flex()
            .flex_col()
            .items_center()
            .justify_center()
            .size_full()
            .bg(rgb(0x1e1e2e))
            .child(
                div()
                    .text_color(rgb(0xcdd6f4))
                    .text_xl()
                    .child("Hello from GPUI!")
            )
    }
}
```

`render` is called when the view is invalidated (not every frame, unlike egui). The element tree is diffed against the previous one; only changed GPU draw calls are re-submitted.

### Putting it together: minimal working app

```rust
use gpui::*;

struct HelloView;

impl Render for HelloView {
    fn render(&mut self, _cx: &mut ViewContext<Self>) -> impl IntoElement {
        div()
            .flex()
            .items_center()
            .justify_center()
            .size_full()
            .bg(rgb(0x1e1e2e))
            .child(
                div()
                    .text_color(rgb(0xcdd6f4))
                    .text_xl()
                    .child("Hello, GPUI!")
            )
    }
}

fn main() {
    App::new().run(|cx: &mut AppContext| {
        cx.open_window(WindowOptions::default(), |cx| {
            cx.new_view(|_cx| HelloView)
        }).unwrap();
    });
}
```

## State management with Model\<T\>

GPUI separates state from views. State lives in `Model<T>` entities managed by the framework. Views hold a `Model<T>` handle and subscribe to changes.

### Creating a model

```rust
struct Counter {
    value: i32,
}

// Inside AppContext or ViewContext:
let counter: Model<Counter> = cx.new_model(|_cx| Counter { value: 0 });
```

### Reading and writing model state

```rust
// Read (inside a view or context closure):
let value = counter.read(cx).value;

// Write — triggers subscribers:
counter.update(cx, |counter, cx| {
    counter.value += 1;
    cx.notify();   // marks views subscribed to this model as dirty
});
```

`cx.notify()` is the signal to GPUI that the model changed and any subscribed views should re-render.

### Subscribing a view to a model

```rust
struct CounterView {
    counter: Model<Counter>,
}

impl CounterView {
    fn new(cx: &mut ViewContext<Self>) -> Self {
        // Subscribe: re-render this view when the counter model changes
        cx.observe(&counter_handle, |_view, _model, cx| {
            cx.notify();
        }).detach();

        Self { counter: counter_handle }
    }
}

impl Render for CounterView {
    fn render(&mut self, cx: &mut ViewContext<Self>) -> impl IntoElement {
        let value = self.counter.read(cx).value;
        div()
            .child(format!("Count: {value}"))
            .on_click(cx.listener(|this, _event, cx| {
                this.counter.update(cx, |c, cx| {
                    c.value += 1;
                    cx.notify();
                });
            }))
    }
}
```

The ownership shape: the view owns a `Model<T>` handle (cheap clone, reference-counted). The framework owns the actual data. Multiple views can hold handles to the same model and all re-render when it changes.

## Element API

GPUI's element API is a fluent builder style. The core primitive is `div()`, styled with method chains:

### Layout

```rust
div()
    .flex()                          // display: flex
    .flex_col()                      // flex-direction: column
    .flex_row()                      // flex-direction: row
    .items_center()                  // align-items: center
    .justify_between()               // justify-content: space-between
    .gap(px(8.0))                    // gap between children
    .w(px(200.0)).h(px(100.0))       // explicit size
    .size_full()                     // width: 100%; height: 100%
    .p(px(16.0))                     // padding
    .m(px(8.0))                      // margin
```

### Appearance

```rust
div()
    .bg(rgb(0x313244))               // background color
    .rounded(px(8.0))                // border-radius
    .border_1()                      // border width
    .border_color(rgb(0x45475a))     // border color
    .shadow_md()                     // drop shadow
    .text_color(rgb(0xcdd6f4))       // text color
    .text_sm()                       // font size
    .font_bold()                     // font weight
```

### Children and text

```rust
div()
    .child("plain text string")
    .child(div().child("nested element"))
    .children(items.iter().map(|item| {
        div().child(item.name.clone())
    }))
```

### Event handlers

```rust
div()
    .on_click(cx.listener(|this, event: &ClickEvent, cx| {
        // handle click
    }))
    .on_hover(cx.listener(|this, is_hovering: &bool, cx| {
        // handle hover state
    }))
    .cursor_pointer()                // show pointer cursor on hover
```

`cx.listener(...)` captures the view reference correctly — don't use plain closures that capture `self` directly.

## Async tasks in GPUI

GPUI has its own async executor built in. Spawn tasks from a context:

```rust
cx.spawn(|view, mut cx| async move {
    // async work here (file I/O, HTTP, etc.)
    let result = do_async_work().await;

    // update view back on the main thread
    cx.update_view(&view, |this, cx| {
        this.result = Some(result);
        cx.notify();
    }).ok();
}).detach();
```

`cx.spawn` returns a `Task<T>`. Calling `.detach()` lets it run without holding the handle. To cancel on drop, keep the `Task` on the struct.

## A complete counter app

```rust
use gpui::*;

struct Counter {
    value: i32,
}

struct CounterView {
    counter: Model<Counter>,
}

impl CounterView {
    fn new(counter: Model<Counter>, cx: &mut ViewContext<Self>) -> Self {
        cx.observe(&counter, |_, _, cx| cx.notify()).detach();
        Self { counter }
    }
}

impl Render for CounterView {
    fn render(&mut self, cx: &mut ViewContext<Self>) -> impl IntoElement {
        let value = self.counter.read(cx).value;

        div()
            .flex()
            .flex_col()
            .items_center()
            .justify_center()
            .size_full()
            .gap(px(16.0))
            .bg(rgb(0x1e1e2e))
            .child(
                div()
                    .text_color(rgb(0xcdd6f4))
                    .text_3xl()
                    .child(format!("{value}"))
            )
            .child(
                div()
                    .flex()
                    .gap(px(8.0))
                    .child(
                        div()
                            .px(px(16.0)).py(px(8.0))
                            .bg(rgb(0x89b4fa))
                            .rounded(px(6.0))
                            .cursor_pointer()
                            .child("-")
                            .on_click(cx.listener(|this, _, cx| {
                                this.counter.update(cx, |c, cx| {
                                    c.value -= 1;
                                    cx.notify();
                                });
                            }))
                    )
                    .child(
                        div()
                            .px(px(16.0)).py(px(8.0))
                            .bg(rgb(0xa6e3a1))
                            .rounded(px(6.0))
                            .cursor_pointer()
                            .child("+")
                            .on_click(cx.listener(|this, _, cx| {
                                this.counter.update(cx, |c, cx| {
                                    c.value += 1;
                                    cx.notify();
                                });
                            }))
                    )
            )
    }
}

fn main() {
    App::new().run(|cx: &mut AppContext| {
        let counter = cx.new_model(|_cx| Counter { value: 0 });
        cx.open_window(WindowOptions::default(), |cx| {
            cx.new_view(|cx| CounterView::new(counter, cx))
        }).unwrap();
    });
}
```

## GPUI vs egui vs iced: when to choose what

| Question | egui | iced | GPUI |
|---|---|---|---|
| Fastest to prototype? | Yes | No | No |
| GPU rendering built-in? | No | No | Yes |
| Explicit state graph? | No | Messages | Model entities |
| Production-stable API? | Yes | Near-stable | No (still maturing) |
| macOS first-class? | Yes | Yes | Yes |
| Best for? | Tools, devtools | Polished apps | Editor-grade apps |

GPUI is the right choice when you are building something like a code editor, data visualization suite, or any app where GPU rendering and a fine-grained reactive state graph are not optional.

## Recap

- `App::new().run(|cx| { ... })` is the entry point; `AppContext` is the runtime handle.
- Views implement `Render`, which returns an element tree diffed and drawn on the GPU.
- State lives in `Model<T>` entities; views subscribe via `cx.observe`; changes notify with `cx.notify()`.
- The element API is a fluent builder: `div().flex().bg(...).child(...)`.
- Use `cx.listener(...)` for event handlers; `cx.spawn(...)` for async tasks.
- GPUI is battle-tested in Zed but its standalone crate API is still stabilizing — expect some churn.
