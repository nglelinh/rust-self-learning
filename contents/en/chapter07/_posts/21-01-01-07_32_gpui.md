If you have ever tried building a complex desktop app in Rust, you quickly hit the classic "UI graph vs. borrow checker" wall: a sidebar needs to read the active chat room, the header needs to show its unread count, and a background WebSocket task needs to push a new message into it—all while the window is rendering. Traditional OOP toolkits solve this with tangled reference-counted pointers and callbacks; Rust refuses to let two places hold `&mut` to the same widget at once.

**GPUI**—the GPU-accelerated framework built for the Zed code editor—solves this problem with an elegant architectural trick borrowed from game engines: **centralized entity ownership**. Instead of widgets owning each other directly, GPUI's `AppContext` owns every piece of state in a flat arena, and views simply hold lightweight, typed handles to them.

## Background Knowledge Map: What Architectural Ideas Power GPUI?

To read and write GPUI code fluently without fighting the compiler, four core ideas do almost all the heavy lifting:

1. **Arena-Owned Entities & Typed Handles (`Model<T>` / `View<V>` / `Entity<T>`)**:
   Rather than storing `Rc<RefCell<Counter>>` everywhere, GPUI stores all state objects inside a single central store owned by the application context (`AppContext` / `App`). Your code holds cheap, copyable/cloneable **handles** (essentially a generational integer ID + a `PhantomData<T>` type marker). To read or mutate the state, you pass the handle back to `cx.update(...)`, which checks dynamically that you are not mutating the same entity re-entrantly—giving you Rust's safety without fighting cyclic lifetimes.

2. **Hybrid Retained State + Immediate-Mode Rendering**:
   GPUI combines the best of both worlds. Application state (`Model<T>` / `Entity<T>`) is **retained** across frames and persists as long as a handle exists. Its visual representation (`Render::render`) is **immediate-like**: whenever `cx.notify()` marks a view dirty, GPUI calls `render(&mut self, cx)` to construct a lightweight tree of `Div` / `Element` values, lays them out with Taffy flexbox, paints them to the GPU, and drops the element tree at the end of the frame.

3. **Reactive Subscriptions & Dirty-Flag Invalidation (`cx.observe`, `cx.notify`)**:
   A GPU app should never burn 100% CPU re-rendering a static window. GPUI tracks explicit observer edges: when View A observes Model B, calling `cx.notify()` inside Model B sets a dirty bit on View A and schedules exactly one frame redraw on the next VSync tick.

4. **Foreground vs. Background Executors (`cx.spawn`, `cx.background_executor()`)**:
   Desktop OS windowing APIs require UI mutations on the **main (foreground) thread**, while network I/O and disk work must run on **background threads** so the UI never freezes. GPUI integrates async tasks directly into its context so a background future can `await` data and seamlessly hop back to the foreground thread to update a model.

## Why GPUI?

The Zed team needed a UI framework that could:

1. Render a code editor with millions of characters without frame drops.
2. Support GPU-accelerated custom drawing (syntax highlighting, minimap, inline AI diffs).
3. Work in a highly concurrent Rust codebase with many async tasks modifying state.
4. Feel productive for the developers building Zed features daily.

No existing Rust framework met all four constraints, so they built GPUI. The result is a framework where the rendering path is always on the GPU (Metal/Vulkan/DirectX), state changes are propagated through an explicit entity graph, and the UI authoring style is close enough to immediate-mode to feel natural.

## Core primitives

### App and AppContext

`App` is the entry point. You create one per process and call `.run()` with a closure that receives an `AppContext`:

```rust
use gpui::*;

fn main() {
    App::new().run(|cx: &mut AppContext| {
        // everything starts here
    });
}
```

`AppContext` (`cx`) is your handle to the GPUI runtime. You use it to open windows, create models, and read/write global state.

### Window

Open a window from inside the `run` closure:

```rust
App::new().run(|cx: &mut AppContext| {
    cx.open_window(
        WindowOptions {
            window_bounds: Some(WindowBounds::Windowed(Bounds {
                origin: point(px(0.0), px(0.0)),
                size: size(px(800.0), px(600.0)),
            })),
            ..Default::default()
        },
        |cx| cx.new_view(|_cx| HelloView),
    ).unwrap();
});
```

`cx.open_window` takes options and a closure that returns the root `View`. A view is the unit of rendering in GPUI.

### View and the Render trait

A view is any struct that implements `Render`. The `render` method returns an element tree:

```rust
struct HelloView;

impl Render for HelloView {
    fn render(&mut self, _cx: &mut ViewContext<Self>) -> impl IntoElement {
        div()
            .flex()
            .flex_col()
            .items_center()
            .justify_center()
            .size_full()
            .bg(rgb(0x1e1e2e))
            .child(
                div()
                    .text_color(rgb(0xcdd6f4))
                    .text_xl()
                    .child("Hello from GPUI!")
            )
    }
}
```

`render` is called when the view is invalidated (not every frame, unlike egui). The element tree is diffed against the previous one; only changed GPU draw calls are re-submitted.

### Putting it together: minimal working app

```rust
use gpui::*;

struct HelloView;

impl Render for HelloView {
    fn render(&mut self, _cx: &mut ViewContext<Self>) -> impl IntoElement {
        div()
            .flex()
            .items_center()

            .child(
                div()

fn main() {
    App::new().run(|cx: &mut AppContext| {
        cx.open_window(WindowOptions::default(), |cx| {

```

## State management with Model\<T\>

GPUI separates state from views. State lives in `Model<T>` entities managed by the framework. Views hold a `Model<T>` handle and subscribe to changes.

### Creating a model

```rust
struct Counter {
    value: i32,
}

// Inside AppContext or ViewContext:
let counter: Model<Counter> = cx.new_model(|_cx| Counter { value: 0 });
```

### Reading and writing model state

```rust
// Read (inside a view or context closure):
let value = counter.read(cx).value;

// Write — triggers subscribers:
counter.update(cx, |counter, cx| {
    counter.value += 1;
    cx.notify();   // marks views subscribed to this model as dirty
});
```

`cx.notify()` is the signal to GPUI that the model changed and any subscribed views should re-render.

### Subscribing a view to a model

```rust
struct CounterView {
    counter: Model<Counter>,
}

impl CounterView {
    fn new(cx: &mut ViewContext<Self>) -> Self {
        // Subscribe: re-render this view when the counter model changes
        cx.observe(&counter_handle, |_view, _model, cx| {
            cx.notify();
        }).detach();

        Self { counter: counter_handle }
    }
}

impl Render for CounterView {
    fn render(&mut self, cx: &mut ViewContext<Self>) -> impl IntoElement {
        let value = self.counter.read(cx).value;
        div()
            .child(format!("Count: {value}"))
            .on_click(cx.listener(|this, _event, cx| {
                this.counter.update(cx, |c, cx| {
                    c.value += 1;
                    cx.notify();
                });
            }))
    }
}
```

The ownership shape: the view owns a `Model<T>` handle (cheap clone, reference-counted). The framework owns the actual data. Multiple views can hold handles to the same model and all re-render when it changes.

## Element API

GPUI's element API is a fluent builder style. The core primitive is `div()`, styled with method chains:

### Layout

```rust
div()
    .flex()                          // display: flex
    .flex_col()                      // flex-direction: column
    .flex_row()                      // flex-direction: row
    .items_center()                  // align-items: center
    .justify_between()               // justify-content: space-between
    .gap(px(8.0))                    // gap between children
    .w(px(200.0)).h(px(100.0))       // explicit size
    .size_full()                     // width: 100%; height: 100%
    .p(px(16.0))                     // padding
    .m(px(8.0))                      // margin
```

### Appearance

```rust
div()
    .bg(rgb(0x313244))               // background color
    .rounded(px(8.0))                // border-radius
    .border_1()                      // border width
    .border_color(rgb(0x45475a))     // border color
    .shadow_md()                     // drop shadow
    .text_color(rgb(0xcdd6f4))       // text color
    .text_sm()                       // font size
    .font_bold()                     // font weight
```

### Children and text

```rust
div()
    .child("plain text string")
    .child(div().child("nested element"))
    .children(items.iter().map(|item| {
        div().child(item.name.clone())
    }))
```

### Event handlers

```rust
div()
    .on_click(cx.listener(|this, event: &ClickEvent, cx| {
        // handle click
    }))
    .on_hover(cx.listener(|this, is_hovering: &bool, cx| {
        // handle hover state
    }))
    .cursor_pointer()                // show pointer cursor on hover
```

`cx.listener(...)` captures the view reference correctly — don't use plain closures that capture `self` directly.

## Async tasks in GPUI

GPUI has its own async executor built in. Spawn tasks from a context:

```rust
cx.spawn(|view, mut cx| async move {
    // async work here (file I/O, HTTP, etc.)
    let result = do_async_work().await;

    // update view back on the main thread
    cx.update_view(&view, |this, cx| {
        this.result = Some(result);
        cx.notify();
    }).ok();
}).detach();
```

`cx.spawn` returns a `Task<T>`. Calling `.detach()` lets it run without holding the handle. To cancel on drop, keep the `Task` on the struct.

### Deep-Dive Explanation: Tracing a GPUI Entity Handle and One `cx.notify()` Frame Cycle (Read Slowly)

Newcomers to GPUI often wonder: *"If `View<Counter>` is just a handle, where does the actual `count: i32` live in memory, and what happens byte-by-byte when I click `+1`?"* Let us trace the exact memory layout and execution sequence by hand.

Suppose our app has one `Counter { count: 0 }` registered in GPUI's central entity table at slot `id = 42`.

#### Step 1: Memory Layout Before the Click

```text
AppContext (Central Entity Arena on Heap)
┌────────────────────────────────────────────────────────┐
│ EntityMap:                                             │
│   slot 42 ──▶ Box<Counter { count: 0 }>  [dirty: false]│
│   observers[42] ──▶ [ ViewHandle(id=42) ]              │
└────────────────────────────────────────────────────────┘

Window Root
  └── root_view: View<Counter> { entity_id: 42, ref_count: 1 }   (only 16 bytes!)
```

Notice why cloning `View<Counter>` into a click handler closure is cheap and borrow-checker-friendly: you are **not** cloning `Counter` or borrowing `&mut Counter`. You are only copying the 16-byte handle (`entity_id: 42`) and incrementing its reference count (`1 → 2`).

#### Step 2: Hand-Tracing the Click Event (`count: 0 → 1`)

Follow every step from the hardware mouse click to the updated pixel on screen:

1. **OS Mouse-Up Event**: macOS/Linux/Windows delivers `MouseUp(x=124, y=68)` to GPUI's window callback on the main thread.
2. **Hit-Testing**: GPUI checks the previous frame's hitboxes and finds that `(124, 68)` falls inside the `+1` button's rectangle `[100..160, 50..85]`.
3. **Listener Invocation (`cx.listener(...)`)**: GPUI temporarily moves `Box<Counter>` out of `EntityMap[42]` (replacing slot 42 with a "currently leased" sentinel so re-entrant borrows panic cleanly instead of causing UB!) and calls your closure with `&mut Counter`:
   - `self.count += 1;` → `count` changes from `0` to `1`.
   - `cx.notify();` → GPUI appends `entity_id = 42` to `window.dirty_views` and requests a VSync redraw from the OS.
4. **Lease Return**: Your closure finishes; GPUI moves `Box<Counter { count: 1 }>` back into `EntityMap[42]`.
5. **Next VSync Tick (within $\le 8.33\text{ ms}$ at 120 Hz)**:
   - GPUI drains `window.dirty_views` (`[42]`), calls `Counter::render(&mut self, cx)`, and receives a fresh tree: `div().child("Count: 1").child(button("+1"))`.
   - **Layout pass**: Taffy computes exact pixel boxes for every `div`.
   - **Prepaint pass**: GPUI records hitboxes (so the next click knows where `+1` is) and shapes `"Count: 1"` into glyph IDs.
   - **Paint pass**: GPUI appends quads and glyph instances into a flat GPU scene buffer and issues a single render pass to Metal/Vulkan.
   - `window.dirty_views` is now empty; CPU usage returns to `0%` until the next event.

Because `Counter::render` is pure description and `EntityMap` mediates all mutation, you get React-like declarative clarity with native Rust memory safety and zero virtual-DOM diffing overhead.

## A complete counter app

```rust
use gpui::*;

struct Counter {
    value: i32,
}

struct CounterView {
    counter: Model<Counter>,
}

impl CounterView {
    fn new(counter: Model<Counter>, cx: &mut ViewContext<Self>) -> Self {
        cx.observe(&counter, |_, _, cx| cx.notify()).detach();
        Self { counter }
    }
}

impl Render for CounterView {
    fn render(&mut self, cx: &mut ViewContext<Self>) -> impl IntoElement {
        let value = self.counter.read(cx).value;

        div()
            .flex()
            .flex_col()
            .items_center()
            .justify_center()
            .size_full()
            .gap(px(16.0))
            .bg(rgb(0x1e1e2e))
            .child(
                div()
                    .text_color(rgb(0xcdd6f4))
                    .text_3xl()
                    .child(format!("{value}"))
            )
            .child(
                div()
                    .flex()
                    .gap(px(8.0))
                    .child(
                        div()
                            .px(px(16.0)).py(px(8.0))
                            .bg(rgb(0x89b4fa))
                            .rounded(px(6.0))
                            .cursor_pointer()
                            .child("-")
                            .on_click(cx.listener(|this, _, cx| {
                                this.counter.update(cx, |c, cx| {
                                    c.value -= 1;
                                    cx.notify();
                                });
                            }))
                    )
                    .child(
                        div()
                            .px(px(16.0)).py(px(8.0))
                            .bg(rgb(0xa6e3a1))
                            .rounded(px(6.0))
                            .cursor_pointer()
                            .child("+")
                            .on_click(cx.listener(|this, _, cx| {
                                this.counter.update(cx, |c, cx| {
                                    c.value += 1;
                                    cx.notify();
                                });
                            }))
                    )
            )
    }
}

fn main() {
    App::new().run(|cx: &mut AppContext| {
        let counter = cx.new_model(|_cx| Counter { value: 0 });
        cx.open_window(WindowOptions::default(), |cx| {
            cx.new_view(|cx| CounterView::new(counter, cx))
        }).unwrap();
    });
}
```

## GPUI vs egui vs iced: when to choose what

| Question | egui | iced | GPUI |
|---|---|---|---|
| Fastest to prototype? | Yes | No | No |
| GPU rendering built-in? | No | No | Yes |
| Explicit state graph? | No | Messages | Model entities |
| Production-stable API? | Yes | Near-stable | No (still maturing) |
| macOS first-class? | Yes | Yes | Yes |
| Best for? | Tools, devtools | Polished apps | Editor-grade apps |

GPUI is the right choice when you are building something like a code editor, data visualization suite, or any app where GPU rendering and a fine-grained reactive state graph are not optional.

## Recap

- `App::new().run(|cx| { ... })` is the entry point; `AppContext` is the runtime handle.
- Views implement `Render`, which returns an element tree diffed and drawn on the GPU.
- State lives in `Model<T>` entities; views subscribe via `cx.observe`; changes notify with `cx.notify()`.
- The element API is a fluent builder: `div().flex().bg(...).child(...)`.
- Use `cx.listener(...)` for event handlers; `cx.spawn(...)` for async tasks.
- GPUI is battle-tested in Zed but its standalone crate API is still stabilizing — expect some churn.
