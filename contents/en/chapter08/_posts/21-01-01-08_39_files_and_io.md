The file descriptor is the OS's universal handle for I/O — files, pipes, sockets, terminals, and devices are all fds. This lesson covers the Unix I/O model, Rust's `std::fs` and `std::io` abstractions, raw `File` operations, and the OS-level calls underneath them.

## 60-minute teaching plan

- 0 to 10 min: The Unix I/O model — file descriptors, the open file table, inheritance.
- 10 to 25 min: `std::fs` — reading, writing, metadata, directory traversal.
- 25 to 40 min: Raw file I/O — `File`, `Read`/`Write`/`Seek` traits, OS-level flags.
- 40 to 55 min: `mmap`-based I/O with `memmap2`; comparing strategies.
- 55 to 60 min: Exercises and recap.

## Learning goals

By the end of this lesson, students can:

- Explain what a file descriptor is and how the OS tracks open files.
- Use `std::fs` for common file tasks and know when to drop down to `File` directly.
- Open files with specific OS flags (`O_CREAT`, `O_APPEND`, `O_EXCL`).
- Memory-map a file and explain when that is faster than `read`/`write`.

## The Unix I/O model

### File descriptors

Every open resource is represented as a small non-negative integer — the **file descriptor (fd)**. Three are always pre-opened:

| fd | Name | Purpose |
|---|---|---|
| 0 | `stdin` | Standard input |
| 1 | `stdout` | Standard output |
| 2 | `stderr` | Standard error |

When you call `open()`, the kernel allocates the next available integer in the process's **file descriptor table** and returns it. That table maps integers to entries in the kernel's **open file table**, which records the file position, open flags, and a reference to the underlying inode.

Key consequence: file descriptors are inherited by child processes (unless marked `O_CLOEXEC`). That's how shells wire up pipes.

### The VFS layer

The **Virtual File System (VFS)** is the kernel abstraction that makes all I/O resources look like files. Whether you're reading a regular file, a socket, a pipe, or `/proc/cpuinfo`, the API is `read(fd, buf, count)` and `write(fd, buf, count)`. Rust's `Read`/`Write` traits mirror this abstraction directly.

## std::fs — the everyday API

### Reading files

```rust
use std::fs;

// Entire file into a String
let text = fs::read_to_string("config.toml")?;

// Entire file into Vec<u8>
let bytes = fs::read("image.png")?;
```

### Writing files

```rust
// Overwrite (creates or truncates)
fs::write("output.txt", "hello\n")?;

// Append with explicit OpenOptions
use std::fs::OpenOptions;
use std::io::Write;

let mut file = OpenOptions::new()
    .append(true)
    .create(true)
    .open("log.txt")?;

writeln!(file, "log entry")?;
```

### Metadata and directory operations

```rust
let meta = fs::metadata("Cargo.toml")?;
println!("size: {} bytes", meta.len());
println!("is dir: {}", meta.is_dir());
println!("modified: {:?}", meta.modified()?);

// Create / remove
fs::create_dir_all("a/b/c")?;
fs::remove_dir_all("a")?;
fs::copy("src.txt", "dst.txt")?;
fs::rename("old.txt", "new.txt")?;

// Iterate directory
for entry in fs::read_dir("src")? {
    let entry = entry?;
    println!("{:?}", entry.path());
}
```

### Recursive directory walk with `walkdir`

```toml
[dependencies]
walkdir = "2"
```

```rust
use walkdir::WalkDir;

for entry in WalkDir::new("src").into_iter().filter_map(|e| e.ok()) {
    if entry.file_type().is_file() {
        println!("{}", entry.path().display());
    }
}
```

## Raw File I/O

`std::fs::File` implements `Read`, `Write`, and `Seek`. Use it when you need streaming access or precise control over buffering.

```rust
use std::fs::File;
use std::io::{BufReader, BufWriter, Read, Write, Seek, SeekFrom};

// Buffered reading — reduces syscall count
let file = File::open("large.log")?;
let reader = BufReader::new(file);
for line in reader.lines() {
    println!("{}", line?);
}

// Buffered writing
let file = File::create("output.bin")?;
let mut writer = BufWriter::new(file);
writer.write_all(&[0u8; 1024])?;
// BufWriter flushes on drop; explicit flush for errors:
writer.flush()?;
```

### Seeking

```rust
let mut file = File::open("data.bin")?;
file.seek(SeekFrom::Start(128))?;     // absolute
file.seek(SeekFrom::Current(-4))?;    // relative to current
file.seek(SeekFrom::End(-8))?;        // relative to end
let pos = file.stream_position()?;    // get current position
```

### OS-level open flags

`OpenOptions` maps directly to `open(2)` flags:

```rust
use std::fs::OpenOptions;

let file = OpenOptions::new()
    .read(true)
    .write(true)
    .create_new(true)   // O_CREAT | O_EXCL — fail if file exists
    .open("lock.pid")?;
```

On Unix you can access additional flags via `std::os::unix::fs::OpenOptionsExt`:

```rust
use std::os::unix::fs::OpenOptionsExt;

let file = OpenOptions::new()
    .write(true)
    .create(true)
    .custom_flags(libc::O_SYNC)   // O_SYNC: flush to disk on every write
    .open("wal.log")?;
```

## Memory-mapped I/O with memmap2

Memory mapping (`mmap`) asks the kernel to map a file's bytes directly into the process's virtual address space. You then read/write it as a byte slice — no `read()`/`write()` syscalls for each access; page faults load data on demand.

```toml
[dependencies]
memmap2 = "0.9"
```

### Read-only map

```rust
use std::fs::File;
use memmap2::Mmap;

let file = File::open("large-dataset.bin")?;
let mmap = unsafe { Mmap::map(&file)? };

// mmap dereferences as &[u8]
let first_four = &mmap[..4];
println!("{first_four:?}");
```

The `unsafe` is required because the OS can unmap or modify the backing file externally, which would be UB through the slice. For files you control, this is safe in practice.

### Read-write map

```rust
use memmap2::MmapMut;

let file = OpenOptions::new().read(true).write(true).open("data.bin")?;
let mut mmap = unsafe { MmapMut::map_mut(&file)? };

mmap[0..4].copy_from_slice(&42u32.to_le_bytes());
mmap.flush()?;   // msync: ensure dirty pages are written to disk
```

### When to use mmap vs read/write

| Scenario | Prefer |
|---|---|
| Reading a large file sequentially once | `BufReader` — simpler, predictable I/O scheduling |
| Random access across a large file | `mmap` — seek is a pointer add, not a syscall |
| Shared memory between processes | `mmap` — map the same file; changes visible across processes |
| Writing append-only logs | `BufWriter` with `O_APPEND` — simpler and safe |
| Parsing a large binary format in-place | `mmap` — zero-copy parsing with `&[u8]` |

## File locking

For coordinating access across processes, use advisory locks (`flock` / `fcntl`):

```toml
[dependencies]
fs2 = "0.4"
```

```rust
use fs2::FileExt;

let file = File::create("app.lock")?;
file.try_lock_exclusive()?;    // returns Err if already locked
// ... critical section ...
file.unlock()?;
```

Advisory locks are not enforced by the kernel — all processes must cooperate and check. For single-writer scenarios, writing your PID to the lock file is a common pattern.

## In-class exercises

1. Write a program that counts the number of lines in a file without reading the entire file into memory.
2. Use `OpenOptions` with `create_new(true)` to implement a simple "lock file" — a program that refuses to start a second instance.
3. Memory-map a file and use the `memchr` crate (or byte search) to count occurrences of a byte value without loading the file into a `Vec`.
4. Write a program that tails a log file: open it, seek to the end, then poll for new bytes appended by another process.

## Recap

- File descriptors are the universal OS I/O handle; `stdin`/`stdout`/`stderr` are fds 0–1–2.
- `std::fs` covers the common case; `File` + `BufReader`/`BufWriter` for streaming; `OpenOptions` for OS-level flags.
- `mmap` maps file bytes into the address space — best for random access and zero-copy parsing.
- Advisory file locks (`fs2`) coordinate multi-process access to shared files.
