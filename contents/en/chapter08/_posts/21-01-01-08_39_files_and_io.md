One of the most enduring design ideas in computer science is Unix's motto: *"Everything is a file."* Whether your Rust program is reading a gigabyte CSV from NVMe, streaming JSON over a TCP socket, writing to a terminal, or receiving bytes from a pipe, the kernel hands you the exact same primitive: a small non-negative integer called a **file descriptor (fd)**.

Yet treating `File::read` as magic can quietly destroy your program's performance—turning a 5-millisecond scan into a 5-second crawl—or cause baffling bugs when two descriptors share a file offset. This lesson opens the hood on the kernel's three-layer file table, buffered I/O, memory-mapped files (`mmap`), and advisory locks.

## Background Knowledge Map: What Three Kernel Structures Sit Behind a Single `File` Handle?

To reason clearly about raw I/O, buffering, `dup()`, and `mmap()`, keep four core OS mechanisms in view:

1. **The Three-Table Kernel File Model**:
   A file descriptor (`fd = 3`) is **not** a pointer to disk blocks. It is an index into three nested kernel structures:
   - **Per-process File Descriptor Table**: maps small integers (`0=stdin`, `1=stdout`, `2=stderr`, `3=...`) to pointers into the system-wide Open File Table.
   - **System-wide Open File Description Table**: stores the current **byte offset**, open flags (`O_RDONLY`, `O_APPEND`, `O_NONBLOCK`), and a pointer to the inode.
   - **Inode / Vnode Table**: stores the actual file metadata (size, permissions, timestamps, pointers to disk blocks in the kernel page cache).

2. **User-Space Buffering vs. System-Call Overhead (`BufReader` / `BufWriter`)**:
   Every unbuffered `read()` or `write()` triggers a **user-to-kernel mode switch** (roughly $200$–$1{,}000\text{ ns}$). `BufReader<File>` amortizes that cost by fetching an $8\text{ KB}$ chunk from the kernel in one syscall and serving subsequent small reads directly from user-space RAM in nanoseconds.

3. **Memory-Mapped I/O (`mmap` / `memmap2`)**:
   Instead of copying bytes from the kernel's page cache into a user-space `Vec<u8>`, `mmap` maps the file's page-cache frames directly into your process's virtual address space. Reads trigger hardware page faults on demand with zero extra copy—but require `unsafe` in Rust because another process could truncate or mutate the underlying file concurrently, violating `&[u8]` immutability guarantees.

4. **Advisory File Locking (`flock` / `fcntl`)**:
   Unix locks are generally *advisory* (cooperating processes agree to acquire a shared read lock or exclusive write lock before touching a file) rather than mandatory—vital for SQLite databases, lockfiles, and concurrent log writers.

## The Unix I/O model

### File descriptors

Every open resource is represented as a small non-negative integer — the **file descriptor (fd)**. Three are always pre-opened:

| fd | Name | Purpose |
|---|---|---|
| 0 | `stdin` | Standard input |
| 1 | `stdout` | Standard output |
| 2 | `stderr` | Standard error |

When you call `open()`, the kernel allocates the next available integer in the process's **file descriptor table** and returns it. That table maps integers to entries in the kernel's **open file table**, which records the file position, open flags, and a reference to the underlying inode.

Key consequence: file descriptors are inherited by child processes (unless marked `O_CLOEXEC`). That's how shells wire up pipes.

### The VFS layer

The **Virtual File System (VFS)** is the kernel abstraction that makes all I/O resources look like files. Whether you're reading a regular file, a socket, a pipe, or `/proc/cpuinfo`, the API is `read(fd, buf, count)` and `write(fd, buf, count)`. Rust's `Read`/`Write` traits mirror this abstraction directly.

## std::fs — the everyday API

### Reading files

```rust
use std::fs;

// Entire file into a String
let text = fs::read_to_string("config.toml")?;

// Entire file into Vec<u8>
let bytes = fs::read("image.png")?;
```

### Writing files

```rust
// Overwrite (creates or truncates)
fs::write("output.txt", "hello\n")?;

// Append with explicit OpenOptions
use std::fs::OpenOptions;
use std::io::Write;

let mut file = OpenOptions::new()
    .append(true)
    .create(true)
    .open("log.txt")?;

writeln!(file, "log entry")?;
```

### Metadata and directory operations

```rust
let meta = fs::metadata("Cargo.toml")?;
println!("size: {} bytes", meta.len());
println!("is dir: {}", meta.is_dir());
println!("modified: {:?}", meta.modified()?);

// Create / remove
fs::create_dir_all("a/b/c")?;
fs::remove_dir_all("a")?;
fs::copy("src.txt", "dst.txt")?;
fs::rename("old.txt", "new.txt")?;

// Iterate directory
for entry in fs::read_dir("src")? {
    let entry = entry?;
    println!("{:?}", entry.path());
}
```

### Recursive directory walk with `walkdir`

```toml
[dependencies]
walkdir = "2"
```

```rust
use walkdir::WalkDir;

for entry in WalkDir::new("src").into_iter().filter_map(|e| e.ok()) {
    if entry.file_type().is_file() {
        println!("{}", entry.path().display());
    }
}
```

## Raw File I/O

`std::fs::File` implements `Read`, `Write`, and `Seek`. Use it when you need streaming access or precise control over buffering.

```rust
use std::fs::File;
use std::io::{BufReader, BufWriter, Read, Write, Seek, SeekFrom};

// Buffered reading — reduces syscall count
let file = File::open("large.log")?;
let reader = BufReader::new(file);
for line in reader.lines() {
    println!("{}", line?);
}

// Buffered writing
let file = File::create("output.bin")?;
let mut writer = BufWriter::new(file);
writer.write_all(&[0u8; 1024])?;
// BufWriter flushes on drop; explicit flush for errors:
writer.flush()?;
```

### Seeking

```rust
let mut file = File::open("data.bin")?;
file.seek(SeekFrom::Start(128))?;     // absolute
file.seek(SeekFrom::Current(-4))?;    // relative to current
file.seek(SeekFrom::End(-8))?;        // relative to end
let pos = file.stream_position()?;    // get current position
```

### OS-level open flags

`OpenOptions` maps directly to `open(2)` flags:

```rust
use std::fs::OpenOptions;

let file = OpenOptions::new()
    .read(true)
    .write(true)
    .create_new(true)   // O_CREAT | O_EXCL — fail if file exists
    .open("lock.pid")?;
```

On Unix you can access additional flags via `std::os::unix::fs::OpenOptionsExt`:

```rust
use std::os::unix::fs::OpenOptionsExt;

let file = OpenOptions::new()
    .write(true)
    .create(true)
    .custom_flags(libc::O_SYNC)   // O_SYNC: flush to disk on every write
    .open("wal.log")?;
```

## Memory-mapped I/O with memmap2

Memory mapping (`mmap`) asks the kernel to map a file's bytes directly into the process's virtual address space. You then read/write it as a byte slice — no `read()`/`write()` syscalls for each access; page faults load data on demand.

```toml
[dependencies]
memmap2 = "0.9"
```

### Read-only map

```rust
use std::fs::File;
use memmap2::Mmap;

let file = File::open("large-dataset.bin")?;
let mmap = unsafe { Mmap::map(&file)? };

// mmap dereferences as &[u8]
let first_four = &mmap[..4];
println!("{first_four:?}");
```

The `unsafe` is required because the OS can unmap or modify the backing file externally, which would be UB through the slice. For files you control, this is safe in practice.

### Read-write map

```rust
use memmap2::MmapMut;

let file = OpenOptions::new().read(true).write(true).open("data.bin")?;
let mut mmap = unsafe { MmapMut::map_mut(&file)? };

mmap[0..4].copy_from_slice(&42u32.to_le_bytes());
mmap.flush()?;   // msync: ensure dirty pages are written to disk
```

### When to use mmap vs read/write

| Scenario | Prefer |
|---|---|
| Reading a large file sequentially once | `BufReader` — simpler, predictable I/O scheduling |
| Random access across a large file | `mmap` — seek is a pointer add, not a syscall |
| Shared memory between processes | `mmap` — map the same file; changes visible across processes |
| Writing append-only logs | `BufWriter` with `O_APPEND` — simpler and safe |
| Parsing a large binary format in-place | `mmap` — zero-copy parsing with `&[u8]` |

## File locking

For coordinating access across processes, use advisory locks (`flock` / `fcntl`):

```toml
[dependencies]
fs2 = "0.4"
```

```rust
use fs2::FileExt;

let file = File::create("app.lock")?;
file.try_lock_exclusive()?;    // returns Err if already locked
// ... critical section ...
file.unlock()?;
```

Advisory locks are not enforced by the kernel — all processes must cooperate and check. For single-writer scenarios, writing your PID to the lock file is a common pattern.

### Deep-Dive Explanation: Tracing Kernel File Offsets (`open` vs. `dup`) and `BufReader` Syscall Math (Read Slowly)

Let us walk through two concrete, hand-verifiable traces that clarify why Unix file I/O behaves the way it does.

#### Part 1: Why `dup()` Shares the File Offset While Two `open()` Calls Do Not

Suppose `/tmp/data.txt` contains the 8 ASCII bytes `"ABCDEFGH"`. Compare two scenarios:

**Scenario A — Two separate `File::open("/tmp/data.txt")` calls (`fd = 3`, `fd = 4`)**:
```text
Process FD Table          System Open File Table              Inode Table
┌─────────┐              ┌───────────────────────────┐       ┌──────────────────┐
│ fd 3 ───┼─────────────▶│ OpenFile #1 (offset = 0)  │──┐    │ Inode 9042       │
│ fd 4 ───┼──────┐       └───────────────────────────┘  ├───▶│ "ABCDEFGH" (8 B) │
└─────────┘      │       ┌───────────────────────────┐  │    └──────────────────┘
                 └──────▶│ OpenFile #2 (offset = 0)  │──┘
                         └───────────────────────────┘
```
1. Read 3 bytes from `fd 3` → gets `"ABC"`; `OpenFile #1.offset` advances `0 → 3`.
2. Read 3 bytes from `fd 4` → `OpenFile #2.offset` is still `0`, so `fd 4` **also** reads `"ABC"`!

**Scenario B — One `File::open` (`fd = 3`) followed by `file.try_clone()` / `dup(3)` (`fd = 4`)**:
```text
Process FD Table          System Open File Table              Inode Table
┌─────────┐              ┌───────────────────────────┐       ┌──────────────────┐
│ fd 3 ───┼────────┬────▶│ OpenFile #1 (offset = 0)  │──────▶│ Inode 9042       │
│ fd 4 ───┼────────┘     └───────────────────────────┘       │ "ABCDEFGH" (8 B) │
└─────────┘                                                  └──────────────────┘
```
1. Read 3 bytes from `fd 3` → gets `"ABC"`; the **shared** `OpenFile #1.offset` advances `0 → 3`.
2. Read 3 bytes from `fd 4` → starts at offset `3`, so `fd 4` reads **`"DEF"`** (not `"ABC"`!). This exact mechanism is why a parent and child process writing to the same redirected log file (`2>&1`) do not overwrite each other's offsets.

#### Part 2: Syscall Arithmetic — Unbuffered 1-Byte Reads vs. `BufReader` on a `1 MB` File

Suppose you scan a $1\text{ MB}$ ($1{,}048{,}576\text{ bytes}$) file one byte at a time, and each `read()` syscall costs $500\text{ ns}$ ($0.5\,\mu\text{s}$):

| Strategy | Buffer Size | Total `read()` Syscalls | Pure Syscall Overhead |
| :--- | :---: | :---: | :---: |
| **Unbuffered `File::read(&mut [0u8; 1])`** | $1\text{ B}$ | $1{,}048{,}576$ | $1{,}048{,}576 \times 0.5\,\mu\text{s} \approx \mathbf{524.3\text{ ms}}$ |
| **`BufReader::new(file)` (default)** | $8{,}192\text{ B}$ ($8\text{ KB}$) | $\frac{1{,}048{,}576}{8{,}192} = \mathbf{128}$ | $128 \times 0.5\,\mu\text{s} = \mathbf{0.064\text{ ms}}$ |

Wrapping `File` in `BufReader` cuts kernel transitions by **$8{,}192\times$**—turning half a second of pure syscall overhead into **64 microseconds** with one line of Rust!

2. Use `OpenOptions` with `create_new(true)` to implement a simple "lock file" — a program that refuses to start a second instance.

## Recap

- File descriptors are the universal OS I/O handle; `stdin`/`stdout`/`stderr` are fds 0–1–2.
- `std::fs` covers the common case; `File` + `BufReader`/`BufWriter` for streaming; `OpenOptions` for OS-level flags.
- `mmap` maps file bytes into the address space — best for random access and zero-copy parsing.
- Advisory file locks (`fs2`) coordinate multi-process access to shared files.
