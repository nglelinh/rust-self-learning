Processes are isolated by design. IPC mechanisms are the controlled holes through that isolation: pipes for streaming data between related processes, Unix domain sockets for bidirectional communication on the same machine, and shared memory for zero-copy high-throughput data exchange.

## 60-minute teaching plan

- 0 to 10 min: IPC taxonomy — why processes need to communicate, and the OS mechanisms.
- 10 to 25 min: Pipes — anonymous pipes, named pipes (FIFOs).
- 25 to 40 min: Unix domain sockets — stream and datagram modes.
- 40 to 55 min: Shared memory — `mmap` with `MAP_SHARED`, `shmem_open`.
- 55 to 60 min: Choosing the right mechanism; exercises and recap.

## Learning goals

By the end of this lesson, students can:

- Build a pipeline of processes connected by anonymous pipes.
- Open a named pipe (FIFO) and use it for unidirectional IPC.
- Create a Unix domain socket server and client.
- Set up a shared memory region between two processes using `mmap`.
- Choose the appropriate IPC mechanism given communication patterns and performance requirements.

## IPC taxonomy

| Mechanism | Direction | Same host | Cross-host | Persistence | Throughput |
|---|---|---|---|---|---|
| Anonymous pipe | Unidirectional | Yes (related) | No | No | High |
| Named pipe (FIFO) | Unidirectional | Yes | No | Filesystem | High |
| Unix socket (stream) | Bidirectional | Yes | No | Filesystem | Very high |
| Unix socket (dgram) | Unidirectional | Yes | No | Filesystem | Very high |
| TCP socket | Bidirectional | Yes | Yes | No | High |
| Shared memory | Bidirectional | Yes | No | Optional | Extreme |
| Signal | Unidirectional | Yes | No | No | Very low (1 int) |

## Anonymous pipes

An anonymous pipe is a kernel buffer with one write end and one read end. It is created before `fork()` / `spawn()` and the two ends are distributed between parent and child.

`std::process::Command` hides the pipe creation, but understanding what happens is important:

```rust
use std::process::{Command, Stdio};
use std::io::{BufRead, BufReader, Write};

// Connect two processes: echo | wc -c
let mut echo = Command::new("echo")
    .arg("hello world")
    .stdout(Stdio::piped())
    .spawn()?;

let wc = Command::new("wc")
    .arg("-c")
    .stdin(echo.stdout.take().unwrap())   // wire echo's stdout → wc's stdin
    .output()?;

echo.wait()?;
println!("byte count: {}", String::from_utf8_lossy(&wc.stdout).trim());
```

### Creating a pipe manually with `nix`

```toml
[dependencies]
nix = { version = "0.29", features = ["pipe", "process"] }
```

```rust
use nix::unistd::{pipe, read, write, close, fork, ForkResult};

let (read_fd, write_fd) = pipe()?;

match unsafe { fork()? } {
    ForkResult::Parent { child } => {
        close(write_fd)?;                  // parent only reads
        let mut buf = [0u8; 64];
        let n = read(read_fd, &mut buf)?;
        println!("parent got: {}", std::str::from_utf8(&buf[..n])?);
        nix::sys::wait::waitpid(child, None)?;
    }
    ForkResult::Child => {
        close(read_fd)?;                   // child only writes
        write(write_fd, b"hello from child")?;
        std::process::exit(0);
    }
}
```

## Named pipes (FIFOs)

A FIFO is a persistent pipe: it appears in the filesystem and unrelated processes can open it by name.

```rust
use std::fs::OpenOptions;
use std::io::{Read, Write};
use nix::unistd::mkfifo;
use nix::sys::stat::Mode;

let path = "/tmp/my_fifo";
mkfifo(path, Mode::S_IRWXU)?;

// Writer process:
let mut f = OpenOptions::new().write(true).open(path)?;
f.write_all(b"hello via fifo")?;

// Reader process (in another terminal or thread):
let mut f = OpenOptions::new().read(true).open(path)?;
let mut buf = String::new();
f.read_to_string(&mut buf)?;
println!("{buf}");
```

`open()` on a FIFO blocks until both ends are opened — this is the rendezvous behavior. Use threads or separate processes to open both ends concurrently.

## Unix domain sockets

Unix sockets provide full-duplex, reliable, ordered byte-stream communication between processes on the same machine, with less overhead than TCP (no IP routing, no checksums).

### Stream socket server

```toml
[dependencies]
tokio = { version = "1", features = ["full"] }
```

```rust
use tokio::net::UnixListener;
use tokio::io::{AsyncReadExt, AsyncWriteExt};

#[tokio::main]
async fn main() -> std::io::Result<()> {
    let path = "/tmp/myapp.sock";
    let _ = std::fs::remove_file(path);   // clean up leftover socket
    let listener = UnixListener::bind(path)?;

    loop {
        let (mut stream, _) = listener.accept().await?;
        tokio::spawn(async move {
            let mut buf = vec![0u8; 1024];
            let n = stream.read(&mut buf).await.unwrap();
            let msg = String::from_utf8_lossy(&buf[..n]);
            println!("received: {msg}");
            stream.write_all(b"ACK").await.unwrap();
        });
    }
}
```

### Stream socket client

```rust
use tokio::net::UnixStream;
use tokio::io::{AsyncReadExt, AsyncWriteExt};

#[tokio::main]
async fn main() -> std::io::Result<()> {
    let mut stream = UnixStream::connect("/tmp/myapp.sock").await?;
    stream.write_all(b"hello from client").await?;

    let mut buf = vec![0u8; 64];
    let n = stream.read(&mut buf).await?;
    println!("server said: {}", String::from_utf8_lossy(&buf[..n]));
    Ok(())
}
```

Unix sockets also support **datagram mode** (like UDP but local) and **passing file descriptors** (`SCM_RIGHTS`) — a technique used by display servers and container runtimes to transfer open files between processes.

## Shared memory

Shared memory is the highest-throughput IPC mechanism: two processes map the same physical pages into their address spaces and read/write directly with no kernel involvement on the data path.

### mmap with MAP_SHARED

Using `memmap2` (from lesson 08-39):

```rust
use memmap2::MmapMut;
use std::fs::OpenOptions;

// Both processes open the same file and map it with MAP_SHARED
let file = OpenOptions::new()
    .read(true)
    .write(true)
    .create(true)
    .open("/tmp/shared_buf")?;
file.set_len(4096)?;   // size the file

let mut mmap = unsafe { MmapMut::map_mut(&file)? };

// Writer:
mmap[..5].copy_from_slice(b"hello");
mmap.flush()?;

// Reader (in another process, same mapping):
let msg = &mmap[..5];
println!("{}", std::str::from_utf8(msg)?);
```

### Synchronization is your responsibility

Shared memory has no built-in synchronization. Two concurrent writers produce a data race. Use:

- **A `Mutex` in shared memory**: `parking_lot` supports this via `unsafe` placement in shared regions.
- **A separate semaphore or condition variable**: e.g. POSIX semaphores via `nix::sys::sem`.
- **Lock-free atomics**: `std::sync::atomic` types can be placed in shared memory if their alignment requirements are met.
- **A ring buffer with memory ordering**: the `crossbeam-queue` `ArrayQueue` is appropriate if both ends are in the same process (for cross-process, manual atomic fences are needed).

### POSIX shared memory objects

For anonymous shared memory (no file on disk) use `shm_open` via `nix`:

```rust
use nix::sys::mman::{shm_open, shm_unlink, mmap, munmap, MapFlags, ProtFlags};
use nix::sys::stat::Mode;
use nix::fcntl::OFlag;
use nix::unistd::ftruncate;

let fd = shm_open(
    "/myapp_shm",
    OFlag::O_CREAT | OFlag::O_RDWR,
    Mode::S_IRWXU,
)?;
ftruncate(&fd, 4096)?;

let ptr = unsafe {
    mmap(None, 4096.try_into()?, ProtFlags::PROT_READ | ProtFlags::PROT_WRITE,
         MapFlags::MAP_SHARED, &fd, 0)?
};

// ptr is *mut std::ffi::c_void — cast to your type and use with care
// Cleanup:
unsafe { munmap(ptr, 4096)?; }
shm_unlink("/myapp_shm")?;
```

POSIX shared memory objects appear under `/dev/shm` on Linux; they are cleaned up on reboot if not explicitly unlinked.

## Choosing the right IPC mechanism

- **Anonymous pipe**: parent-child data streaming, shell-style pipelines.
- **Named pipe (FIFO)**: simple unidirectional bus between unrelated processes; log aggregation.
- **Unix socket**: bidirectional RPC or event bus between processes on the same machine; daemon/client protocols (systemd, Docker).
- **Shared memory**: highest throughput — video frames, sensor data, ring buffers in real-time systems. Always pair with synchronization.
- **TCP socket**: needed only when processes are on different machines, or when you want a standard protocol other tools can speak.

## In-class exercises

1. Build a two-process pipeline in Rust: process A generates Fibonacci numbers, process B receives them over an anonymous pipe and writes the even ones to stdout.
2. Write a named pipe producer that appends one line per second to a FIFO, and a consumer that reads and timestamps each line.
3. Implement a Unix socket echo server (using `std::os::unix::net::UnixListener`, sync version) and a client that sends 100 messages and measures round-trip latency.
4. Set up a shared memory ring buffer: writer process fills it with u64 counters; reader process reads them and reports how many it received per second.

## Recap

- Anonymous pipes stream data between related processes; `Command::stdout(Stdio::piped())` uses them.
- FIFOs extend pipes to unrelated processes via a filesystem path.
- Unix sockets give full-duplex reliable streams (or datagrams) on a single machine — lower overhead than TCP.
- Shared memory is zero-copy between processes but requires explicit synchronization.
- Choosing IPC: pipes for streams, sockets for RPC, shared memory for high-throughput data.
