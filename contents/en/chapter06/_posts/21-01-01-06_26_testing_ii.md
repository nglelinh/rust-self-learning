Beyond example-based tests, Rust code benefits from systematically testing invariants and edge cases. This lesson teaches the property-testing mindset — finding bugs that no specific test case would catch — and how to choose high-value targets.

## 60-minute teaching plan

- 0 to 10 min: Why example tests miss bugs (combinatorial inputs).
- 10 to 25 min: Invariants and contracts (what should always be true).
- 25 to 40 min: Property-testing mindset: generate many cases and assert invariants.
- 40 to 55 min: Mini-lab: write 5 invariants for a module and encode them as tests.
- 55 to 60 min: Fuzzing targets and recap.

## Learning goals

By the end of this lesson, students can:

- Identify invariants for a type or algorithm.
- Write tests that check properties across many inputs.
- Separate pure logic from IO so properties are easy to test.
- Choose good fuzz/property targets (parsers, serializers, reducers).

## Key concept: why example tests miss bugs

Consider a function `sort(xs: &mut Vec<i32>)`. How many tests would you write?

```rust
#[test] fn sort_empty()   { ... }
#[test] fn sort_one()     { ... }
#[test] fn sort_two()     { ... }
#[test] fn sort_reverse() { ... }
#[test] fn sort_already_sorted() { ... }
```

A buggy sort might pass all of these if the bug only manifests for:

- Lists of a specific length (e.g., exactly 7 elements)
- Specific value distributions (e.g., all values the same)
- Lists with repeated elements
- Lists with `i32::MIN` or `i32::MAX`

You cannot enumerate all cases. **Invariants** let you test properties across the entire input space.

## Invariants: what to test

An **invariant** is a statement that should always hold — for any valid input.

### Types of invariants

| Type | Example |
|------|---------|
| **Structural** | `sorted(xs)` → every adjacent pair satisfies `xs[i] <= xs[i+1]` |
| **Round-trip** | `parse(render(x)) == Ok(x)` |
| **Monotonicity** | `add_item(stats, x)` → `stats.count` increases by 1 |
| **Safety** | `parse(any_input)` never panics |
| **Idempotence** | `normalize(normalize(x)) == normalize(x)` |
| **Bijection** | `encode` and `decode` are inverses |

### Examples from earlier lessons

From the stats module:

- `min <= max` (when at least one item exists)
- `count == 0` implies `mean.is_none()`
- After `add(x)`, `count` is exactly one more than before
- After adding `k` items, `min <= xs[i] <= max` for all items added

From `take_chars`:

- `take_chars(s, n)` is always a valid UTF-8 string
- `s.starts_with(take_chars(s, n))` — it's a prefix
- `take_chars(s, n).chars().count() <= n`

From `top_k`:

- Result length is `min(k, input.len())`
- Result is sorted by count descending, then word ascending
- All words in the result appeared in the input

## Property testing without a crate

Even without `proptest`/`quickcheck`, you can get significant value by running over generated inputs in a loop.

### Testing `sort`

```rust
fn is_sorted(xs: &[i32]) -> bool {
    xs.windows(2).all(|w| w[0] <= w[1])
}

fn contains_same_elements(orig: &[i32], sorted: &[i32]) -> bool {
    let mut a = orig.to_vec(); a.sort();
    let mut b = sorted.to_vec(); b.sort();
    a == b
}

#[test]
fn sort_is_always_sorted() {
    let test_cases: Vec<Vec<i32>> = vec![
        vec![],
        vec![1],
        vec![3, 1, 2],
        vec![5, 4, 3, 2, 1],
        vec![1, 1, 1, 1],
        vec![i32::MIN, 0, i32::MAX],
        vec![2, 2, 1, 2, 2],
    ];

    for mut xs in test_cases {
        let original = xs.clone();
        xs.sort();
        assert!(is_sorted(&xs), "not sorted: {:?}", xs);
        assert!(contains_same_elements(&original, &xs), "lost elements: {:?}", original);
    }
}
```

### Testing `take_chars`

```rust
fn take_chars(s: &str, n: usize) -> &str {
    let end = s.char_indices().nth(n).map_or(s.len(), |(i, _)| i);
    &s[..end]
}

#[test]
fn take_chars_properties() {
    let inputs = ["", "a", "hello", "héllo", "日本語", "a b  c", "🦀🦀🦀"];

    for s in &inputs {
        for n in 0..10 {
            let t = take_chars(s, n);
            // Invariant 1: is a prefix
            assert!(s.starts_with(t), "'{t}' is not a prefix of '{s}'");
            // Invariant 2: char count <= n
            assert!(t.chars().count() <= n, "'{t}' has more than {n} chars");
            // Invariant 3: valid UTF-8 (implicit — &str is always valid)
            // Invariant 4: idempotence — taking again gives the same result
            assert_eq!(take_chars(t, n), t);
        }
    }
}
```

### Testing a round-trip serializer

```rust
#[derive(Debug, Clone, PartialEq)]
struct Point { x: i32, y: i32 }

fn serialize(p: &Point) -> String { format!("{},{}", p.x, p.y) }

fn deserialize(s: &str) -> Result<Point, &'static str> {
    let (x, y) = s.split_once(',').ok_or("missing comma")?;
    Ok(Point {
        x: x.parse().map_err(|_| "bad x")?,
        y: y.parse().map_err(|_| "bad y")?,
    })
}

#[test]
fn point_round_trip() {
    let points = [
        Point { x: 0, y: 0 },
        Point { x: i32::MIN, y: i32::MAX },
        Point { x: -100, y: 42 },
    ];

    for p in &points {
        let serialized = serialize(p);
        let deserialized = deserialize(&serialized).expect("round-trip failed");
        assert_eq!(*p, deserialized, "round-trip failed for {:?}", p);
    }
}
```

## Designing for property tests

Rules:

- Make **pure functions** small and testable (no IO, no randomness).
- Push side effects to the boundary.
- Return **structured types** so invariants are easy to express.

```rust
// Easy to property-test (pure):
fn top_k(words: &[&str], k: usize) -> Vec<(String, usize)> { ... }

// Hard to property-test (mixes IO):
fn top_k_from_file(path: &str, k: usize) -> Vec<(String, usize)> { ... }
```

## Mini-lab: 5 invariants for one module

### Module: `Stats` (running statistics)

```rust
#[derive(Debug, Default)]
struct Stats {
    count: usize,
    sum:   i64,
    min:   Option<i64>,
    max:   Option<i64>,
}

impl Stats {
    fn add(&mut self, x: i64) {
        self.count += 1;
        self.sum += x;
        self.min = Some(self.min.map_or(x, |m| m.min(x)));
        self.max = Some(self.max.map_or(x, |m| m.max(x)));
    }

    fn mean(&self) -> Option<f64> {
        if self.count == 0 { None }
        else { Some(self.sum as f64 / self.count as f64) }
    }
}
```

### The 5 invariants as tests

```rust
#[cfg(test)]
mod stats_invariants {
    use super::*;

    // Invariant 1: empty stats have no mean
    #[test]
    fn empty_stats_has_no_mean() {
        let s = Stats::default();
        assert_eq!(s.count, 0);
        assert!(s.mean().is_none());
        assert!(s.min.is_none());
        assert!(s.max.is_none());
    }

    // Invariant 2: count matches number of add() calls
    #[test]
    fn count_tracks_additions() {
        let inputs = [1i64, -5, 0, 100, 42];
        let mut s = Stats::default();
        for (i, &x) in inputs.iter().enumerate() {
            s.add(x);
            assert_eq!(s.count, i + 1);
        }
    }

    // Invariant 3: min <= max when count > 0
    #[test]
    fn min_le_max() {
        let cases = vec![
            vec![1i64],
            vec![5, 3, 7, 1],
            vec![i64::MIN, i64::MAX],
            vec![42, 42, 42],
        ];
        for case in cases {
            let mut s = Stats::default();
            for &x in &case { s.add(x); }
            assert!(s.min.unwrap() <= s.max.unwrap(), "case: {:?}", case);
        }
    }

    // Invariant 4: min and max are actually in the input
    #[test]
    fn min_max_in_input() {
        let inputs = [5i64, 3, 7, 1, 9, 2];
        let mut s = Stats::default();
        for &x in &inputs { s.add(x); }
        assert!(inputs.contains(&s.min.unwrap()));
        assert!(inputs.contains(&s.max.unwrap()));
    }

    // Invariant 5: mean is within [min, max]
    #[test]
    fn mean_between_min_and_max() {
        let cases: &[&[i64]] = &[
            &[1, 2, 3, 4, 5],
            &[0, 100],
            &[-50, 50],
        ];
        for &case in cases {
            let mut s = Stats::default();
            for &x in case { s.add(x); }
            let mean = s.mean().unwrap();
            let min  = s.min.unwrap() as f64;
            let max  = s.max.unwrap() as f64;
            assert!(mean >= min && mean <= max,
                "mean {mean} not in [{min}, {max}] for {:?}", case);
        }
    }
}
```

## Using `proptest` for automated input generation

The `proptest` crate generates hundreds of random inputs and shrinks failures to minimal examples.

Add to `Cargo.toml`:

```toml
[dev-dependencies]
proptest = "1"
```

Rewrite `take_chars` property tests with proptest:

```rust
use proptest::prelude::*;

proptest! {
    #[test]
    fn take_chars_is_prefix(s in ".*", n in 0usize..20) {
        let t = take_chars(&s, n);
        prop_assert!(s.starts_with(t));
        prop_assert!(t.chars().count() <= n);
    }

    #[test]
    fn stats_count_matches_additions(inputs in prop::collection::vec(i64::MIN..=i64::MAX, 0..100)) {
        let mut s = Stats::default();
        for &x in &inputs { s.add(x); }
        prop_assert_eq!(s.count, inputs.len());
    }
}
```

When a property fails, proptest automatically shrinks the input to the minimal failing case — invaluable for debugging.

## Fuzzing: where it shines

**Fuzzing** is automated randomized testing focused on crashes, panics, assertion failures, and hangs.

Great fuzz targets:

- **Parsers** (text → AST): any input should be handled without panic
- **Decoders** (bytes → struct): invalid bytes should return `Err`, not crash
- **Reducers/simplifiers**: monotonicity and idempotence properties
- **Serialization round-trips**: `parse(encode(x)) == Ok(x)` for all `x`

### Rust fuzzing tools

- `cargo-fuzz` (uses libFuzzer)
- `afl.rs` (uses AFL)

Basic fuzz target:

```rust
// fuzz/fuzz_targets/parse_command.rs
#![no_main]
use libfuzzer_sys::fuzz_target;

fuzz_target!(|data: &[u8]| {
    if let Ok(s) = std::str::from_utf8(data) {
        // Must never panic — all inputs should return Ok or Err, not crash
        let _ = parse_command(s);
    }
});
```

Teaching point: the fuzz target just calls your parser with random bytes. Any panic is a bug.

## Applications in systems programming

### Testing a network packet parser

```rust
#[test]
fn dns_packet_roundtrip() {
    let packets = [
        DnsQuery::new("example.com", RecordType::A),
        DnsQuery::new("rust-lang.org", RecordType::AAAA),
    ];
    for pkt in &packets {
        let bytes = pkt.to_bytes();
        let parsed = DnsQuery::from_bytes(&bytes).expect("round-trip failed");
        assert_eq!(*pkt, parsed);
    }
}

#[test]
fn dns_parser_does_not_panic_on_garbage() {
    let inputs: &[&[u8]] = &[b"", b"\x00", b"\xff\xff\xff\xff"];
    for &input in inputs {
        let _ = DnsQuery::from_bytes(input);  // must not panic
    }
}
```

### Testing a compression algorithm

```rust
#[test]
fn compress_decompress_roundtrip() {
    let data_cases: &[&[u8]] = &[
        b"",
        b"hello",
        b"aaaaaaaaaaaaaaaa",  // runs
        b"\x00\x01\x02\xff", // binary
    ];
    for &data in data_cases {
        let compressed = compress(data);
        let decompressed = decompress(&compressed).unwrap();
        assert_eq!(data, decompressed.as_slice());
    }
}

#[test]
fn compress_is_idempotent() {
    let data = b"hello world";
    let c1 = compress(data);
    let c2 = compress(data);
    assert_eq!(c1, c2);  // deterministic
}
```

## Challenges and extensions

1. **`proptest` strategy composition**: generate a `Vec<Point>` with at least one element and test that `bounding_box` returns a box that contains all points.

2. **Differential testing**: implement two versions of a function (naive and optimized) and assert they always agree:
   ```rust
   proptest! {
       #[test]
       fn naive_and_optimized_agree(input in /* ... */) {
           assert_eq!(naive_sort(&input), optimized_sort(&input));
       }
   }
   ```

3. **Shrinking in proptest**: artificially break a function to create a failure. Observe how proptest shrinks the input to the minimal failing case. What does it shrink to?

4. **Fuzz a real parser**: write a fuzz target for the `parse_command` function from lesson 25. What inputs does it fail on?

## Common mistakes

1. Only testing happy paths.
2. Writing invariants that are **too weak** (always true regardless of the function).
3. Writing invariants that are **too strong** (actually false for some valid inputs).
4. Using randomness without determinism in tests → flaky results. Use `proptest` (which uses a seeded PRNG) rather than `rand::random()`.
5. Testing properties only with small inputs — many bugs appear only at scale.

## Recap

- Invariants are the core of high-signal tests — they hold across all inputs.
- Property testing checks invariants across many generated inputs.
- Round-trip, idempotence, and monotonicity are the most valuable invariant families.
- Design pure functions so properties are easy to assert.
- Fuzzing is most valuable on parsers, decoders, and protocol implementations.
