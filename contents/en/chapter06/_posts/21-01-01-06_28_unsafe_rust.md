`unsafe` does not mean "dangerous by default". It means **you must uphold specific invariants the compiler cannot check**. This lesson teaches what `unsafe` enables, how to write safety contracts, and how to encapsulate unsafe code behind safe APIs so the rest of your codebase stays fully verified.

## 60-minute teaching plan

- 0 to 10 min: What `unsafe` is (and what it is not).
- 10 to 25 min: Raw pointers and the invariants they require.
- 25 to 40 min: Encapsulation: keeping `unsafe` small and local.
- 40 to 55 min: Mini-lab: implement a small unsafe optimization with a safe wrapper.
- 55 to 60 min: Auditing checklist and recap.

By the end of this lesson, students can:

- Explain what `unsafe` permits (and what it does not).

## Key concept: what `unsafe` actually means

In safe Rust, the compiler enforces six guarantees:

1. No dangling references
2. No data races
3. No null pointer dereferences
4. No aliasing violations (at most one mutable reference at a time)
5. No invalid values (e.g., `bool` must be 0 or 1)
6. No uninitialized reads

`unsafe` is a way to say: "Compiler, I'm doing something here that you can't verify statically. I promise I've checked the invariants manually."

### What `unsafe` enables

- **Dereferencing raw pointers** (`*const T`, `*mut T`)
- **Calling `unsafe fn`**
- **Accessing or modifying mutable statics**
- **Implementing unsafe traits** (like `Send`, `Sync`)
- **Accessing union fields**

### What `unsafe` does NOT disable

- The borrow checker still runs — safe references within `unsafe` blocks are still checked.
- Type checking still runs.
- The rest of Rust's type system is fully active.

```rust
unsafe {
    let x = 5;
    let r = &x;      // still valid — borrow checker still works
    println!("{}", r);
}
```

Teaching point: `unsafe` unlocks specific low-level operations. It doesn't turn Rust into C.

## Raw pointers

Raw pointers are like C pointers:

- Can be null
- Have no lifetime tracking
- Can point to freed or invalid memory
- Multiple mutable raw pointers to the same location are allowed

```rust
let x: i32 = 42;
let p: *const i32 = &x;       // create raw pointer from reference
let q: *mut i32 = &x as *const i32 as *mut i32;  // const → mut cast (dangerous)
```

Creating raw pointers is safe. **Dereferencing** them is unsafe:

```rust
let x = 10i32;
let p: *const i32 = &x;
unsafe {
    println!("{}", *p);  // safe here: p is valid, aligned, initialized
}
```

### Invariants you must uphold when dereferencing

When you dereference `*p`, you promise:

1. `p` is **non-null**.
2. `p` points to **valid memory** for type `T`.
3. `p` is **properly aligned** for type `T` (e.g., `*const i32` aligned to 4 bytes).
4. The memory is **initialized** with a valid `T` value.
5. No **aliasing violation**: if `p` is `*mut T`, no other reference to the same memory exists while you're using `p`.
6. The memory remains valid for the **duration** of the access.

This is the "Stacked Borrows" / aliasing model. Violating any of these is **undefined behavior** — the compiler may generate incorrect code.

## Unsafe function contracts

An `unsafe fn` is a promise to the caller: "you must uphold these preconditions."

```rust
/// # Safety
/// The caller must ensure:
/// - `ptr` is non-null and points to at least `len` initialized `u8` values.
/// - `len` is at most `isize::MAX`.
/// - No other mutable reference to the same memory exists during the call.
unsafe fn bytes_to_str(ptr: *const u8, len: usize) -> &'static str {
    let slice = std::slice::from_raw_parts(ptr, len);
    std::str::from_utf8_unchecked(slice)
}
```

The `/// # Safety` doc comment is the Rust convention for documenting `unsafe fn`. Tools like Clippy warn if you call an `unsafe fn` without a safety comment.

## Encapsulation: safe wrapper around unsafe core

The correct pattern:

1. Make a **public safe function** with normal Rust types.
2. Put `unsafe` in a **tiny private helper** with documented invariants.
3. The safe wrapper **validates inputs** before calling the unsafe helper.
4. **Test** the public function like any other.

## Mini-lab: unsafe byte search

Goal: implement `find_byte(haystack, needle)` that returns the first index of `needle` using raw pointer arithmetic.

### Step 1: safe reference implementation

```rust
fn find_byte_safe(h: &[u8], needle: u8) -> Option<usize> {
    h.iter().position(|&b| b == needle)
}
```

This is the correctness reference. We'll test our unsafe version against it.

### Step 2: unsafe core

```rust
/// # Safety
/// - `h` must be a valid slice (non-null, aligned, initialized).
/// This invariant is upheld by the safe public wrapper.
unsafe fn find_byte_raw(h: &[u8], needle: u8) -> Option<usize> {
    let ptr = h.as_ptr();
    let len = h.len();

    for i in 0..len {
        // Safety:
        // - `i < len` ensures `ptr.add(i)` is within the slice bounds.
        // - The slice's memory is valid for reads for `len` bytes (from caller's guarantee).
        let b = unsafe { *ptr.add(i) };
        if b == needle {
            return Some(i);
        }
    }
    None
}
```

Teaching point: even within the `unsafe` function, each unsafe operation gets its own safety justification comment.

### Step 3: safe public wrapper

```rust
/// Find the first occurrence of `needle` in `h`.
/// Returns the index, or `None` if not found.
pub fn find_byte(h: &[u8], needle: u8) -> Option<usize> {
    // Safety: `h` is a valid Rust slice — all invariants are satisfied.
    unsafe { find_byte_raw(h, needle) }
}
```

The safe wrapper's job: validate inputs (the slice is already a valid Rust type, so no extra validation needed here) and document why it's safe to call the unsafe inner function.

### Step 4: tests using differential testing

```rust
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn find_byte_matches_safe_all_values() {
        let h = b"hello, world! \x00\xff";
        for needle in 0u8..=255 {
            assert_eq!(
                find_byte(h, needle),
                find_byte_safe(h, needle),
                "mismatch for needle = {needle}"
            );
        }
    }

    #[test]
    fn find_byte_empty_slice() {
        assert_eq!(find_byte(b"", b'x'), None);
    }

    #[test]
    fn find_byte_first_element() {
        assert_eq!(find_byte(b"abc", b'a'), Some(0));
    }

    #[test]
    fn find_byte_last_element() {
        assert_eq!(find_byte(b"abc", b'c'), Some(2));
    }

    #[test]
    fn find_byte_not_found() {
        assert_eq!(find_byte(b"abc", b'z'), None);
    }

    #[test]
    fn find_byte_repeated_returns_first() {
        assert_eq!(find_byte(b"aabba", b'a'), Some(0));
    }
}
```

Teaching point: **differential testing** — comparing against a safe reference implementation — is one of the best strategies for testing unsafe code. If they agree on all inputs, the unsafe code is likely correct.

## Code walkthrough: naive → idiomatic

### Naive: unnecessary unsafe

```rust
unsafe fn set_bit(byte: &mut u8, bit: u8) {
    *byte |= 1 << bit;
}
```

This doesn't need to be `unsafe fn`. The `&mut u8` borrow is already checked by the borrow checker.

### Idiomatic: only mark `unsafe fn` when the caller must uphold invariants

```rust
fn set_bit(byte: &mut u8, bit: u8) {
    assert!(bit < 8, "bit index out of range");
    *byte |= 1 << bit;
}
```

Keep `unsafe fn` for functions where callers must actually provide safety guarantees — not just any function with a raw pointer argument.

### When unsafe is justified: zero-copy string creation

```rust
use std::str;

/// Create a `&str` from bytes known to be valid UTF-8.
///
/// # Safety
/// `bytes` must be valid UTF-8. If in doubt, use `str::from_utf8` instead.
pub unsafe fn from_utf8_unchecked(bytes: &[u8]) -> &str {
    // Safety: caller guarantees valid UTF-8
    str::from_utf8_unchecked(bytes)
}

// Safe wrapper that validates
pub fn from_utf8(bytes: &[u8]) -> Result<&str, str::Utf8Error> {
    str::from_utf8(bytes)
}
```

The unsafe version avoids the validation overhead when you've already verified UTF-8 validity through other means (e.g., you know the bytes come from a Rust `String` that was split at a char boundary).

## Common patterns in the standard library

Understanding how `std` uses `unsafe` helps you write better unsafe code.

### `Vec::push` (simplified)

```rust
// Conceptually:
unsafe fn push_raw<T>(vec: &mut Vec<T>, item: T) {
    if vec.len == vec.cap {
        // reallocate (complex, omitted)
    }
    // Safety: we just ensured capacity; ptr.add(len) is valid and aligned
    let ptr = vec.ptr.add(vec.len);
    ptr.write(item);
    vec.len += 1;
}
```

### `slice::split_at_unchecked`

```rust
/// # Safety
/// `mid` must be <= `self.len()`
pub unsafe fn split_at_unchecked(&self, mid: usize) -> (&[T], &[T]) {
    // ... creates two slices without bounds check
}
```

Safe version: `split_at` (does bounds check, panics if mid > len). Unsafe version: skips the check for performance-critical paths.

## Applications in systems programming

### SIMD acceleration

SIMD (Single Instruction, Multiple Data) operations work on entire vectors of values simultaneously. They require unsafe because:

- Platform-specific instructions must be used correctly.
- Alignment requirements must be manually verified.

```rust
#[cfg(target_arch = "x86_64")]
unsafe fn count_spaces_simd(s: &str) -> usize {
    // Use x86 SSE2 instructions to process 16 bytes at a time
    // Safety: target feature is checked at compile time via cfg
    todo!()
}
```

### Operating system calls

`libc` functions have C contracts that Rust can't verify:

```rust
use libc::{mmap, munmap, PROT_READ, PROT_WRITE, MAP_ANON, MAP_PRIVATE};

pub struct MmapBuffer {
    ptr: *mut u8,
    len: usize,
}

impl MmapBuffer {
    pub fn new(len: usize) -> std::io::Result<Self> {
        let ptr = unsafe {
            mmap(
                std::ptr::null_mut(),
                len,
                PROT_READ | PROT_WRITE,
                MAP_ANON | MAP_PRIVATE,
                -1, 0,
            )
        };
        if ptr == libc::MAP_FAILED {
            return Err(std::io::Error::last_os_error());
        }
        Ok(Self { ptr: ptr as *mut u8, len })
    }
}

impl Drop for MmapBuffer {
    fn drop(&mut self) {
        unsafe { munmap(self.ptr as *mut _, self.len); }
    }
}
```

### Custom allocators

`#[global_allocator]` and `Allocator` trait (nightly) let you replace the default allocator. These require `unsafe impl` because allocators must uphold strict invariants about returned pointers.

## Auditing checklist

When reviewing unsafe code (your own or others'):

- [ ] Is the `unsafe` block as **small** as possible?
- [ ] Are safety preconditions **documented** in a `// Safety:` comment?
- [ ] Are invariants checked **before** the unsafe operation?
- [ ] Is there a **safe reference implementation** to compare against?
- [ ] Are edge cases covered (empty input, max values, boundary indices)?
- [ ] Are mutable aliasing rules respected?
- [ ] Are raw pointers aligned correctly for the target type?
- [ ] Is all memory accessed still valid (not freed/moved) at the time of access?

### Tools to help

- `cargo clippy` — catches some unsafe misuse.
- `miri` — Rust's undefined behavior checker (runs your tests under a UB detector):
  ```bash
  cargo +nightly miri test
  ```
- `sanitizers` (AddressSanitizer, MemorySanitizer) — run via:
  ```bash
  RUSTFLAGS="-Z sanitizer=address" cargo test
  ```

## Common mistakes

1. Using `unsafe` for performance without measuring — safe Rust is often equally fast.
2. Spreading unsafe code across the codebase instead of concentrating it.
3. Missing edge cases (empty input, pointer at end of allocation).
4. Not writing `// Safety:` comments — makes future audits impossible.
5. Treating `unsafe` as "opt-out of Rust" rather than "manually maintained invariants".

## Recap

- `unsafe` is a promise: you uphold invariants the compiler can't verify.
- Keep `unsafe` blocks small and concentrated in private helpers.
- Document every safety precondition with `// Safety:` comments.
- Test unsafe code against safe reference implementations.
- Use `miri` to catch undefined behavior in your test suite.
- Prefer safe Rust unless you have a clear, measured reason for `unsafe`.
