The capstone ties everything together: design, implementation, testing, documentation, and a polished deliverable. This lesson is about choosing a scope you can finish, applying what you've learned across the full course, and shipping something with good engineering hygiene.

## 60-minute teaching plan

- 0 to 10 min: Pick a project scope that is realistic.
- 10 to 25 min: Define MVP, constraints, and success criteria.
- 25 to 40 min: Design the crate structure and module boundaries.
- 40 to 55 min: Testing + error strategy + docs checklist.
- 55 to 60 min: Next steps: milestones for the next sessions.

## Learning goals

By the end of this lesson, students can:

- Define an MVP with clear input/output behavior.
- Choose a crate layout that supports testing and refactoring.
- Pick an error-handling strategy and apply it consistently.
- Create a README that makes the tool usable.

## Key concept: the gap between "it works" and "it's done"

A Rust program that compiles and produces correct output is halfway done. The rest is:

- **Error handling**: what happens when things go wrong?
- **Edge cases**: empty input, invalid UTF-8, missing files, network timeouts?
- **Testability**: can you refactor without fear?
- **Documentation**: can someone else (or future-you) use this?
- **Observability**: can you understand what it's doing in production?

The capstone is an opportunity to practice all of this on a project of your own.

## Choose a project (pick one)

Each option exercises a different subset of the course. Pick the one that matches your interests and uses concepts you want to reinforce.

### Option 1: Log analyzer (sync, Ch 1-3 heavy)

Reads log files, computes statistics, produces a report.

**Core concepts**: file IO, string parsing, error handling, `HashMap`, iterators.

**MVP spec**:
- Input: one or more log file paths (CLI args)
- Output: per-file statistics (line count, error count, most frequent error type)
- Error cases: missing file, malformed line (skip with a warning)

**Stretch goals**: filter by time range, output as JSON, colorized terminal output.

### Option 2: File indexer (sync, Ch 2-4 heavy)

Walks a directory tree, indexes filenames/metadata, supports queries.

**Core concepts**: `std::fs`, recursion, ownership-friendly APIs, `HashMap`/`BTreeMap`.

**MVP spec**:
- Input: root directory path + query string (CLI args)
- Output: list of matching file paths
- Error cases: permission denied (skip), cycle detection

**Stretch goals**: index by content (`grep`-like), persistence to disk (JSON/CSV).

### Option 3: Async URL fetcher (Ch 5 heavy)

Fetches multiple URLs with timeouts, reports statuses in a table.

**Core concepts**: Tokio, `async`/`.await`, `join_all`, timeouts, error handling.

**MVP spec**:
- Input: `fetch <url>...` (one or more URLs)
- Output: one line per URL: `URL\tSTATUS_CODE\tLATENCY_MS`
- Error cases: timeout (print `TIMEOUT`), network error (print `ERROR: <msg>`)

**Stretch goals**: `--timeout` flag, `--json` output, `--concurrency N` flag, retry with backoff.

### Option 4: Mini key-value store (Ch 4-5 heavy)

In-memory store with optional persistence, accessed via a simple CLI or REPL.

**Core concepts**: `HashMap`, error handling, channels, optionally serialization.

**MVP spec**:
- Commands: `get <key>`, `set <key> <value>`, `delete <key>`, `list`, `quit`
- Output: values on `get`, `OK` on `set`/`delete`, key list on `list`
- Error cases: missing key, invalid command

**Stretch goals**: persistence to a JSON file on `Ctrl-C`, TTL for keys, `watch <key>` (async).

## Define MVP (write this before coding)

Before writing a single line of code, answer these questions:

### Input
- Where does data come from? (CLI args, stdin, a file, a socket)
- What format? (text, binary, structured)
- What are valid inputs? What are invalid inputs?

### Output
- What does success look like? (print to stdout, write a file, return exit code 0)
- What does failure look like? (print to stderr, return non-zero exit code)
- Is output deterministic? (important for tests)

### Errors
- What errors are expected? (file not found, network timeout, invalid input)
- How are errors reported? (stderr, exit code, structured error output)
- Which errors are fatal vs recoverable?

### Example MVP doc (async fetcher)

```markdown
## Async URL Fetcher MVP

**Command**: `fetch <url>...`

**Output format** (one line per URL, tab-separated):
  <url>\t<status_code>\t<latency_ms>

**Error output** (one line per URL):
  <url>\tTIMEOUT\t-           (if timeout fires)
  <url>\tERROR\t-             (if connection refused or other error)

**Exit codes**:
  0 = all URLs succeeded (2xx or 3xx)
  1 = at least one URL failed or timed out

**Constraints**:
  - Default timeout: 10 seconds per URL
  - All URLs fetched concurrently
  - Output order matches input order
```

Writing this forces you to make decisions before you're in the middle of implementation.

## Architecture: crate structure

### The `lib + bin` pattern

Always separate library logic from the binary entry point:

```
src/
  lib.rs      ← all logic goes here (testable)
  main.rs     ← parse args, call lib, print results, exit
  cli.rs      ← argument parsing (clap, argh, etc.)
  domain.rs   ← core data types (structs, enums)
  engine.rs   ← core logic (pure when possible)
  error.rs    ← typed errors
```

Why:

- `src/lib.rs` is visible to `tests/` — integration tests test the lib, not main.
- `src/main.rs` can be thin: parse args → call engine → handle result → exit.
- You can add benchmarks (`benches/`) or examples (`examples/`) that import from lib.

### Module guidelines

| Module | Responsibility | Avoid putting |
|--------|---------------|---------------|
| `domain` | Data types | Business logic, IO |
| `engine` | Core algorithm | IO, CLI concerns |
| `cli` | Arg parsing, output formatting | Business logic |
| `error` | Error types, `Display` impls | Program logic |
| `main` | Wires everything together | Any logic |

## Error strategy

Pick one approach before you start and apply it consistently.

### Option A: module-local typed errors

Each module has its own error type; they're composed upward:

```rust
// error.rs
#[derive(Debug, thiserror::Error)]
pub enum FetchError {
    #[error("network error: {0}")]
    Network(#[from] reqwest::Error),

    #[error("timed out after {secs} seconds")]
    Timeout { secs: u64 },

    #[error("invalid URL: {0}")]
    InvalidUrl(String),
}
```

### Option B: one crate-level error enum

Good for small projects — one `AppError` that covers everything.

### Rules (both options)

- **Never `unwrap()` on user inputs** — always convert to `Err(...)`.
- **Provide context**: which file failed, which URL timed out, which line was malformed.
- **Use `thiserror` for library code**, `anyhow` for binary/application code.

```toml
[dependencies]
thiserror = "1"   # derive Error + Display
anyhow = "1"      # for binary code: anyhow::Result, context(), bail!
```

## Testing strategy

Minimum test suite for any capstone project:

```
5+ unit tests for pure logic
2+ integration tests for CLI or public API behavior
1+ property/invariant test
```

### Where to put tests

```
src/
  engine.rs      ← #[cfg(test)] mod tests { ... }
tests/
  integration.rs ← use my_crate::...; tests public API
```

### Design for testability from the start

```rust
// Engine function: pure, testable
pub fn compute_stats(lines: &[&str]) -> Stats { ... }

// IO function: calls engine, not directly tested
pub fn compute_stats_from_file(path: &str) -> Result<Stats, AppError> {
    let content = std::fs::read_to_string(path)?;
    let lines: Vec<&str> = content.lines().collect();
    Ok(compute_stats(&lines))
}
```

Test `compute_stats` with inline strings. Test `compute_stats_from_file` with tempfile in integration tests.

### Async testing

```rust
#[tokio::test]
async fn fetch_returns_status_for_valid_url() {
    // Use a local mock server (e.g., wiremock crate) for reliable tests
    let mock = MockServer::start().await;
    Mock::given(method("GET")).respond_with(ResponseTemplate::new(200)).mount(&mock).await;

    let result = fetch_url(&mock.uri()).await;
    assert_eq!(result.status, 200);
}
```

## Documentation checklist

Your README should include:

```markdown
# Tool Name

One sentence: what this tool does.

## Install

```bash
cargo install --path .
```

## Usage

```bash
tool-name [FLAGS] [OPTIONS] <INPUT>...
```

## Examples

```bash
# Fetch two URLs with a 5 second timeout
tool-name https://example.com https://rust-lang.org --timeout 5

# Output:
# https://example.com    200    142
# https://rust-lang.org  200    89
```

## Exit codes

| Code | Meaning |
|------|---------|
| 0 | All operations succeeded |
| 1 | At least one operation failed |

## Known limitations

- Does not follow redirects more than 3 times.
- IPv6 addresses not yet supported.
```

## Delivery checklist (definition of done)

Before calling a capstone project "done":

### Code quality
- [ ] `cargo fmt` — no formatting warnings
- [ ] `cargo clippy -- -D warnings` — no Clippy warnings
- [ ] `cargo test` — all tests green

### Error handling
- [ ] No `unwrap()` on user-controlled inputs
- [ ] All error variants have `Display` messages
- [ ] Errors include context (which file, which URL, which field)

### Testing
- [ ] ≥ 5 unit tests for core logic
- [ ] ≥ 2 integration tests
- [ ] ≥ 1 property/invariant test
- [ ] Error paths tested (not just happy paths)

### Documentation
- [ ] README with install + examples
- [ ] At least 2 working examples in README
- [ ] Exit codes documented

### Stretch goals (bonus)
- [ ] `--help` output (via `clap` or `argh`)
- [ ] Progress indicators for long operations
- [ ] `--json` or `--csv` output option

## Multi-session implementation plan

For large capstones, break into sessions:

### Session 1: foundation
- Define all types in `domain.rs`
- Implement `engine.rs` with at least one complete function and tests
- Set up error module

### Session 2: integration
- Wire `main.rs` + `cli.rs`
- Add integration tests
- Handle all error paths

### Session 3: polish
- Add property tests
- Complete README
- Add stretch goals
- Run `cargo clippy`, `cargo fmt`, `cargo test`

## Code walkthrough: log analyzer skeleton

Here's a minimal skeleton to start from:

```rust
// src/domain.rs
#[derive(Debug, Default)]
pub struct FileStats {
    pub lines:      usize,
    pub errors:     usize,
    pub warnings:   usize,
    pub top_errors: Vec<(String, usize)>,
}

// src/engine.rs
use crate::domain::FileStats;

pub fn analyze(text: &str) -> FileStats {
    let mut stats = FileStats::default();
    let mut error_counts = std::collections::HashMap::<String, usize>::new();

    for line in text.lines() {
        stats.lines += 1;
        if line.contains("ERROR") {
            stats.errors += 1;
            let msg = extract_error_type(line);
            *error_counts.entry(msg).or_insert(0) += 1;
        } else if line.contains("WARN") {
            stats.warnings += 1;
        }
    }

    let mut top: Vec<_> = error_counts.into_iter().collect();
    top.sort_by(|a, b| b.1.cmp(&a.1).then(a.0.cmp(&b.0)));
    stats.top_errors = top.into_iter().take(5).collect();
    stats
}

fn extract_error_type(line: &str) -> String {
    // Simplified: take the word after "ERROR"
    line.split_once("ERROR")
        .and_then(|(_, rest)| rest.split_whitespace().next())
        .unwrap_or("UNKNOWN")
        .to_string()
}

// src/engine tests
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn analyze_counts_lines() {
        let text = "INFO start\nERROR timeout\nWARN retry\n";
        let s = analyze(text);
        assert_eq!(s.lines, 3);
        assert_eq!(s.errors, 1);
        assert_eq!(s.warnings, 1);
    }

    #[test]
    fn analyze_top_errors_sorted() {
        let text = "ERROR timeout\nERROR timeout\nERROR oom\n";
        let s = analyze(text);
        assert_eq!(s.top_errors[0].0, "timeout");
        assert_eq!(s.top_errors[0].1, 2);
    }

    #[test]
    fn analyze_empty_is_ok() {
        let s = analyze("");
        assert_eq!(s.lines, 0);
        assert_eq!(s.errors, 0);
    }
}

// src/main.rs
use std::process;
use my_log_analyzer::engine::analyze;

fn main() {
    let args: Vec<String> = std::env::args().skip(1).collect();
    if args.is_empty() {
        eprintln!("Usage: log-analyzer <file>...");
        process::exit(1);
    }

    let mut had_error = false;
    for path in &args {
        match std::fs::read_to_string(path) {
            Ok(text) => {
                let stats = analyze(&text);
                println!("{}: {} lines, {} errors, {} warnings", path, stats.lines, stats.errors, stats.warnings);
                for (err_type, count) in &stats.top_errors {
                    println!("  {}: {}", err_type, count);
                }
            }
            Err(e) => {
                eprintln!("Error reading {}: {}", path, e);
                had_error = true;
            }
        }
    }

    process::exit(if had_error { 1 } else { 0 });
}
```

## Applications: what capstone projects teach

Capstone projects force integration of everything you've learned:

| Course concept | Where it appears |
|----------------|-----------------|
| Ownership | Data flows through the pipeline — who owns what? |
| Borrowing | `analyze(text: &str)` borrows — no unnecessary copies |
| Error handling | `Result` at every IO boundary |
| Traits | `Display` for errors, `Iterator` for data processing |
| Lifetimes | Borrowed views for parsing, owned for storage |
| Collections | `HashMap` for stats, `Vec` for results |
| Testing | Pure engine tested independently from IO |

---

## Recap

- Define MVP before coding — constraints make decisions easier.
- Use `lib + bin` so logic is testable independently of `main`.
- Apply typed errors consistently throughout.
- Test pure logic with unit tests; test IO integration with integration tests.
- A good README is part of the deliverable — write it before you think you're done.
- Ship something small but polished over something large but broken.
