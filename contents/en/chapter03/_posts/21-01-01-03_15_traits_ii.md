Imagine building a log pipeline where users pick output formats—JSON, CSV, or colored terminal text—from a config file at **runtime**. If you try to push `JsonFormatter` and `CsvFormatter` into the same `Vec<T>`, Rust stops you cold: a `Vec<T>` must store elements of one uniform concrete size, and `JsonFormatter` might be 16 bytes while `CsvFormatter` is 40 bytes!

This is the classic fork in the road of Rust abstraction: **static dispatch** (`impl Trait` / `<T: Trait>`, zero-cost monomorphization) versus **dynamic dispatch** (`&dyn Trait` / `Box<dyn Trait>`, runtime polymorphism via fat pointers and vtables). This lesson demystifies the exact memory layout of trait objects, explains object safety in plain language, and gives you a crisp engineering rule for choosing between them.

---

## Background Knowledge Map: Static vs. Dynamic Polymorphism in Systems Languages

Choosing between `<T: Trait>` and `dyn Trait` touches three core systems-programming concepts.

### 1. Memory Layout: Thin Pointers vs. Fat Pointers
A normal reference `&T` is a **thin pointer** (8 bytes on 64-bit CPUs): just a memory address. A trait object reference `&dyn Trait` (or `Box<dyn Trait>`) is a **fat pointer** (16 bytes): **8 bytes** pointing to the concrete data on the stack/heap, plus **8 bytes** pointing to a compiler-generated **vtable** (table of function pointers, size, alignment, and drop glue).
- **Core questions:** Why is `dyn Trait` unsized (`!Sized`)? Why must it always sit behind a pointer (`&dyn`, `Box<dyn>`, `Arc<dyn>`)?
- **Real-world reach:** Plugin architectures, heterogeneous UI widget trees, and `Box<dyn std::error::Error>` error erasure.

### 2. CPU Branching, Inlining, and Binary Bloat
**Static dispatch** copies and specializes machine code for every concrete type—enabling aggressive CPU inlining and SIMD vectorization at the cost of larger binaries and slower compile times. **Dynamic dispatch** emits *one* copy of the function that jumps indirectly through the vtable—keeping binaries small and compile times fast at the cost of one pointer indirection per call.
- **Core questions:** When does vtable indirection actually matter (tight inner loops) vs. vanish into noise (network/disk I/O)?
- **Real-world reach:** Compiler codegen tuning, fast incremental builds, and high-throughput packet processors.

### 3. Object Safety (Dyn-Compatibility)
Not every trait can be turned into `dyn Trait`. If a trait method returns `Self` by value (unknown size at runtime!) or has its own generic type parameter `fn foo<U>(&self, x: U)` (which would require an *infinite* vtable!), Rust marks the trait **not object-safe**.
- **Core questions:** Why is `Clone` not object-safe while `Debug` and `Read` are?
- **Real-world reach:** Designing clean library traits that support both static and dynamic callers.

## Static dispatch: generics

With generics, the compiler generates specialized code per concrete type (monomorphization).

```rust
fn render<T: Normalize>(x: &T) -> String {
    x.normalize()
}
```

Pros:

- Often fastest (inlining, no virtual calls)
- Errors caught at compile time

Cons:

- Can increase compile time and code size
- Cannot easily store multiple types in one `Vec<T>` unless `T` is one concrete type

## Dynamic dispatch: trait objects

Trait objects let you treat many concrete types uniformly at runtime.

Two common forms:

- `&dyn Trait`: borrowed trait object
- `Box<dyn Trait>`: owned trait object (heap allocated)

### Borrowed trait object

```rust
fn print_normalized(x: &dyn Normalize) {
    println!("{}", x.normalize());
}
```

### Owned trait object

Use `Box<dyn Trait>` when you need to store it:

```rust
let xs: Vec<Box<dyn Normalize>> = vec![
    Box::new("  hi ".to_string()),
    Box::new(42i32),
];
```

Teaching points:

- `Box` gives a stable size so it can live in a `Vec`.
- Calls go through a vtable (one level of indirection).

## When to choose what

Rules of thumb:

- Use generics when:
  - call sites know the concrete type
  - performance is critical
  - you don't need heterogenous collections

- Use trait objects when:
  - you want plugin-like behavior
  - you need a `Vec` of mixed implementations
  - you want to choose implementations at runtime (config-driven)

## Mini-lab: pluggable output formatter

Goal: define a formatter trait and implement two output formats.

### Step 1: define a domain type

```rust
#[derive(Debug, Clone, PartialEq, Eq)]
struct Item {
    word: String,
    count: u64,
}
```

### Step 2: define the formatter trait

```rust
trait Formatter {
    fn format(&self, items: &[Item]) -> String;
}
```

Note: `format` takes a slice, not a `Vec`, for flexibility.

### Step 3: implement plain text

```rust
struct Plain;

impl Formatter for Plain {
    fn format(&self, items: &[Item]) -> String {
        let mut out = String::new();
        for it in items {
            out.push_str(&format!("{}\t{}\n", it.word, it.count));
        }
        out
    }
}
```

### Step 4: implement JSON-ish (no external deps)

We keep it simple (not a full JSON serializer), but the pattern is what matters.

{% raw %}
```rust
struct Json;

impl Formatter for Json {
    fn format(&self, items: &[Item]) -> String {
        let mut out = String::from("[");
        for (i, it) in items.iter().enumerate() {
            if i > 0 {
                out.push(',');
            }
            // naive escaping for teaching: replace quotes
            let w = it.word.replace('"', "\\\"");
            out.push_str(&format!("{{\"word\":\"{}\",\"count\":{}}}", w, it.count));
        }
        out.push(']');
        out
    }
}
```
{% endraw %}

Teaching point: in real code you would use `serde_json`, but the trait-object pattern is the focus.

### Step 5: choose formatter at runtime

```rust
fn pick_formatter(name: &str) -> Box<dyn Formatter> {
    match name {
        "json" => Box::new(Json),
        _ => Box::new(Plain),
    }
}
```

### Step 6: wire it together

```rust
fn main() {
    let items = vec![
        Item { word: "a".to_string(), count: 2 },
        Item { word: "b".to_string(), count: 1 },
    ];

    let fmt = pick_formatter("json");
    println!("{}", fmt.format(&items));
}
```

## Object safety (keep it simple)

A trait can be turned into a trait object only if it is object-safe. The basic intuition:

- methods must not use generic type parameters
- methods must not return `Self` (unless behind indirection)

If you hit an object-safety error, it’s usually a sign you should use generics instead.

## Common mistakes

1. Using `Box<dyn Trait>` everywhere (often unnecessary).
2. Using trait objects when generics would be simpler.
3. Designing traits that are not object-safe, then fighting the compiler.

## Worked Examples & Deep Dive

### Worked Example 1: Exact Byte Layout of `Vec<Box<dyn Formatter>>` on a 64-bit Machine

Suppose `JsonFormatter` is 8 bytes (one `bool` + padding) and `CsvFormatter` is 24 bytes (one `String` delimiter). Look at what lives on the **stack** versus the **heap** when you build `let v: Vec<Box<dyn Formatter>> = vec![Box::new(json), Box::new(csv)]`:

| Location | Contents | Size (64-bit) |
|---|---|---|
| Stack: `v` (`Vec` header) | `(ptr, len=2, cap=2)` | **24 bytes** |
| Heap buffer of `v`: slot `[0]` | Fat pointer `(data_ptr -> JsonFormatter, vtable_ptr -> JSON_VTABLE)` | **16 bytes** |
| Heap buffer of `v`: slot `[1]` | Fat pointer `(data_ptr -> CsvFormatter, vtable_ptr -> CSV_VTABLE)` | **16 bytes** |
| Heap allocation #1 | `JsonFormatter` concrete fields | **8 bytes** |
| Heap allocation #2 | `CsvFormatter` concrete fields | **24 bytes** |

Every slot inside `Vec`'s contiguous buffer has the **exact same 16-byte width** (one fat pointer), even though the underlying concrete structs have totally different sizes!

### Worked Example 2: Testing Object Safety on 3 Trait Methods by Hand

Suppose you want to construct `Box<dyn Plugin>`. Check each method signature:
1. `fn name(&self) -> &str;` — takes `&self`, no generic parameters, known return size (`16` bytes for `&str`). **Object-safe ✓**
2. `fn duplicate(&self) -> Self;` — returns `Self` by value! Behind `dyn Plugin`, the caller does *not* know how many stack bytes `Self` needs! **Not object-safe ✗** (Fix: return `Box<dyn Plugin>` or add `where Self: Sized` to exempt it from `dyn`.)
3. `fn log<T: Display>(&self, msg: T);` — generic method parameter `T` could be called with infinitely many types, so `rustc` cannot build a finite vtable! **Not object-safe ✗** (Fix: accept `msg: &dyn Display`.)

### Deep-Dive Explanation: Choosing Between Generics and `dyn Trait` (Read Slowly)

#### Step 1: Default to generics (`<T: Trait>`) inside hot paths and libraries
Generics give callers zero-cost performance *and* maximum flexibility (a caller can always pass `&dyn Trait` into a generic if `Trait` is implemented for `&dyn Trait`, whereas a `dyn Trait` parameter forces dynamic dispatch on everyone).

#### Step 2: Switch to `dyn Trait` the moment you need runtime heterogeneity
If a single collection must mix different concrete types (`Vec<Box<dyn Handler>>`), or the concrete type depends on a runtime CLI flag/config file, generics cannot represent a single uniform type—`dyn Trait` (or a closed `enum`) is the right tool.

#### Step 3: Consider a closed `enum` when the set of variants is fixed
If you only ever have 3 known formatters (`enum Output { Json(JsonFmt), Csv(CsvFmt), Text(TextFmt) }`), an `enum` gives you runtime heterogeneity **with zero heap allocation and zero vtable indirection**! Reach for `dyn Trait` when the set of implementations must stay **open** to external plugins.

#### Step 4: Use `dyn Trait` strategically to cut compile times
Monomorphizing giant generic stacks (`Service<Layer1<Layer2<Layer3<...>>>>`) can blow up compile times and binary size. Inserting a single `Box<dyn Trait>` boundary at a cold I/O seam (like an HTTP router handler) slashes compilation cost while adding nanoseconds next to millisecond network calls.

## Recap

- Generics: compile-time specialization, fast, but not heterogenous.
- Trait objects: runtime polymorphism, flexible, good for plugins.
- Choose based on whether you need runtime selection or mixed collections.
