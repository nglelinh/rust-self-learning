Choosing between generics and trait objects is a common design decision that affects performance, compile times, and API ergonomics. This lesson teaches the tradeoffs and gives you a concrete pattern: plugin-like behavior via `dyn Trait`.

## 60-minute teaching plan

- 0 to 10 min: Two ways to use traits: static dispatch (generics) vs dynamic dispatch (trait objects).
- 10 to 25 min: Generics and monomorphization intuition.
- 25 to 40 min: Trait objects: `&dyn Trait` and `Box<dyn Trait>`.
- 40 to 55 min: Mini-lab: pluggable formatter (plain vs JSON-ish).
- 55 to 60 min: Object safety and recap.

## Learning goals

By the end of this lesson, students can:

- Explain why generics produce faster code (often) but larger binaries.
- Use `dyn Trait` to store different implementations in one collection.
- Choose between `&dyn Trait` and `Box<dyn Trait>`.
- Recognize basic object-safety constraints.

## Static dispatch: generics

With generics, the compiler generates specialized code per concrete type (monomorphization).

```rust
fn render<T: Normalize>(x: &T) -> String {
    x.normalize()
}
```

Pros:

- Often fastest (inlining, no virtual calls)
- Errors caught at compile time

Cons:

- Can increase compile time and code size
- Cannot easily store multiple types in one `Vec<T>` unless `T` is one concrete type

## Dynamic dispatch: trait objects

Trait objects let you treat many concrete types uniformly at runtime.

Two common forms:

- `&dyn Trait`: borrowed trait object
- `Box<dyn Trait>`: owned trait object (heap allocated)

### Borrowed trait object

```rust
fn print_normalized(x: &dyn Normalize) {
    println!("{}", x.normalize());
}
```

### Owned trait object

Use `Box<dyn Trait>` when you need to store it:

```rust
let xs: Vec<Box<dyn Normalize>> = vec![
    Box::new("  hi ".to_string()),
    Box::new(42i32),
];
```

Teaching points:

- `Box` gives a stable size so it can live in a `Vec`.
- Calls go through a vtable (one level of indirection).

## When to choose what

Rules of thumb:

- Use generics when:
  - call sites know the concrete type
  - performance is critical
  - you don't need heterogenous collections

- Use trait objects when:
  - you want plugin-like behavior
  - you need a `Vec` of mixed implementations
  - you want to choose implementations at runtime (config-driven)

## Mini-lab: pluggable output formatter

Goal: define a formatter trait and implement two output formats.

### Step 1: define a domain type

```rust
#[derive(Debug, Clone, PartialEq, Eq)]
struct Item {
    word: String,
    count: u64,
}
```

### Step 2: define the formatter trait

```rust
trait Formatter {
    fn format(&self, items: &[Item]) -> String;
}
```

Note: `format` takes a slice, not a `Vec`, for flexibility.

### Step 3: implement plain text

```rust
struct Plain;

impl Formatter for Plain {
    fn format(&self, items: &[Item]) -> String {
        let mut out = String::new();
        for it in items {
            out.push_str(&format!("{}\t{}\n", it.word, it.count));
        }
        out
    }
}
```

### Step 4: implement JSON-ish (no external deps)

We keep it simple (not a full JSON serializer), but the pattern is what matters.

{% raw %}
```rust
struct Json;

impl Formatter for Json {
    fn format(&self, items: &[Item]) -> String {
        let mut out = String::from("[");
        for (i, it) in items.iter().enumerate() {
            if i > 0 {
                out.push(',');
            }
            // naive escaping for teaching: replace quotes
            let w = it.word.replace('"', "\\\"");
            out.push_str(&format!("{{\"word\":\"{}\",\"count\":{}}}", w, it.count));
        }
        out.push(']');
        out
    }
}
```
{% endraw %}

Teaching point: in real code you would use `serde_json`, but the trait-object pattern is the focus.

### Step 5: choose formatter at runtime

```rust
fn pick_formatter(name: &str) -> Box<dyn Formatter> {
    match name {
        "json" => Box::new(Json),
        _ => Box::new(Plain),
    }
}
```

### Step 6: wire it together

```rust
fn main() {
    let items = vec![
        Item { word: "a".to_string(), count: 2 },
        Item { word: "b".to_string(), count: 1 },
    ];

    let fmt = pick_formatter("json");
    println!("{}", fmt.format(&items));
}
```

## Tests

```rust
#[test]
fn plain_formatter() {
    let items = [Item { word: "x".to_string(), count: 1 }];
    let s = Plain.format(&items);
    assert!(s.contains("x\t1"));
}

#[test]
fn json_formatter_has_brackets() {
    let items = [Item { word: "x".to_string(), count: 1 }];
    let s = Json.format(&items);
    assert!(s.starts_with('[') && s.ends_with(']'));
}
```

## Object safety (keep it simple)

A trait can be turned into a trait object only if it is object-safe. The basic intuition:

- methods must not use generic type parameters
- methods must not return `Self` (unless behind indirection)

If you hit an object-safety error, it’s usually a sign you should use generics instead.

## Common mistakes

1. Using `Box<dyn Trait>` everywhere (often unnecessary).
2. Using trait objects when generics would be simpler.
3. Designing traits that are not object-safe, then fighting the compiler.

## Exercises

1. Add a third formatter: CSV.
2. Make `pick_formatter` read from a string input like `--format=json`.

## Recap

- Generics: compile-time specialization, fast, but not heterogenous.
- Trait objects: runtime polymorphism, flexible, good for plugins.
- Choose based on whether you need runtime selection or mixed collections.
