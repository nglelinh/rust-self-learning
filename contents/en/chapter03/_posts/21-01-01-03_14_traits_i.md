In object-oriented languages like Java or C++, sharing behavior across unrelated types usually means climbing an inheritance hierarchy—`class FileLogger extends BaseLogger`—and paying for virtual method tables at runtime even when the concrete type is known at compile time. Rust throws out class inheritance completely and replaces it with **traits**: crisp behavioral contracts that compose cleanly across structs, enums, and even built-in primitives like `i32` or `str`, compiling down to zero-cost machine code.

This lesson shows what traits really are under the hood, how to define and implement them cleanly, how trait bounds unlock reusable generic functions, and why blanket implementations let one single `impl` block empower thousands of types at once.

---

## Background Knowledge Map: What PL Concepts Sit Behind Rust Traits?

Traits are not just “interfaces with a new name”—they unite three foundational ideas from programming-language theory and systems compilation.

### 1. Ad-Hoc Polymorphism & Typeclasses
Borrowed from Haskell’s **typeclasses**, a Rust trait separates **data layout** (`struct`/`enum`) from **behavior** (`impl Trait for Type`). Unlike OOP inheritance, you can implement your own trait on someone else’s type (or a standard-library trait on your own type) without modifying the original type’s memory layout.
- **Core questions:** How do we write one algorithm that works on any type supporting comparison, formatting, or normalization?
- **Real-world reach:** `Iterator`, `Serialize`/`Deserialize` (`serde`), `Display`, and `From`/`Into` across the entire Rust ecosystem.

### 2. Monomorphization & Zero-Cost Static Dispatch
When you call a generic function `fn process<T: Normalize>(x: T)` with `String` and `Vec<u8>`, the Rust compiler generates **two specialized machine-code functions** (`process::<String>` and `process::<Vec<u8>>`)—a process called **monomorphization**. Every trait method call resolves at compile time and can be fully inlined!
- **Core questions:** Why does generic Rust run as fast as hand-written C? What is the compile-time and binary-size tradeoff?
- **Real-world reach:** High-frequency trading engines, game loops, embedded firmware, and zero-overhead numeric libraries.

### 3. Coherence & the Orphan Rule
To guarantee that every type has at most **one** unambiguous implementation of a given trait across an entire dependency graph, Rust enforces the **orphan rule**: you may implement `Trait` for `Type` only if *either* `Trait` or `Type` is defined in your own crate.
- **Core questions:** Why does Rust forbid implementing `std::fmt::Display` directly for `Vec<i32>`? How does the **newtype pattern** (`struct MyVec(Vec<i32>)`) solve it cleanly?
- **Real-world reach:** Safe crate composition in Cargo workspaces with hundreds of transitive dependencies.

## What a trait is

A trait is a contract: "types that implement this trait provide these methods." It is Rust’s way to express interfaces.

## Define a small trait: `Normalize`

We will create a trait that produces a normalized string representation.

```rust
pub trait Normalize {
    fn normalize(&self) -> String;
}
```

Teaching points:

- `&self` means normalization doesn’t need to consume the value.
- Returning `String` means we produce owned output.

## Implement the trait for multiple types

### For `str` and `String`

```rust
impl Normalize for str {
    fn normalize(&self) -> String {
        self.trim().to_lowercase()
    }
}

impl Normalize for String {
    fn normalize(&self) -> String {
        self.as_str().normalize()
    }
}
```

Teaching points:

- Implementing for `str` makes it work for `&str`.
- Reuse implementations instead of duplicating logic.

### For numbers

```rust
impl Normalize for i32 {
    fn normalize(&self) -> String {
        self.to_string()
    }
}
```

Discuss: normalization for numbers is domain-specific; the point is that traits let you define "what you mean".

## Use it from a generic function

Trait bounds let you write reusable functions:

```rust
pub fn normalized_pair<A: Normalize, B: Normalize>(a: &A, b: &B) -> (String, String) {
    (a.normalize(), b.normalize())
}
```

Or with `impl Trait`:

```rust
pub fn normalized(x: &impl Normalize) -> String {
    x.normalize()
}
```

Teaching point: `impl Trait` in arguments is mostly syntax sugar for a generic bound.

## Default methods

Default methods reduce boilerplate:

```rust
pub trait Normalize {
    fn normalize(&self) -> String;

    fn normalize_nonempty(&self) -> Option<String> {
        let s = self.normalize();
        if s.is_empty() { None } else { Some(s) }
    }
}
```

Teaching points:

- Default methods can call required methods.
- This encourages small traits with composable helpers.

## Blanket impls (conceptual intro)

A blanket impl implements a trait for any type that meets a condition.

Example idea:

```rust
pub trait Describe {
    fn describe(&self) -> String;
}

impl<T: std::fmt::Debug> Describe for T {
    fn describe(&self) -> String {
        format!("{:?}", self)
    }
}
```

Instructor note: this is powerful but can confuse beginners if overused. Mention it as a capability, not as a default pattern.

## Tests

```rust
#[test]
fn normalize_str() {
    assert_eq!("  HeLLo ".normalize(), "hello".to_string());
}

#[test]
fn normalize_string() {
    let s = "  Hi ".to_string();
    assert_eq!(s.normalize(), "hi".to_string());
}
```

Teaching point: trait methods are just methods; once a trait is in scope, you can call them naturally.

## Common mistakes

1. Making one huge trait instead of several small ones.
2. Using traits when a plain function would be simpler.
3. Returning `&str` from normalization when you allocate anyway.

## Worked Examples & Deep Dive

### Worked Example 1: Tracing Monomorphization by Hand (Zero-Cost Generic Calls)

Suppose you write one generic function with a trait bound:

```rust
fn double_score<T: Score>(item: &T) -> u32 {
    item.points() * 2
}
```

And you call it twice in `main()`: once with `Quiz { raw: 40 }` and once with `Bonus(15)`. Watch what `rustc` emits during monomorphization:

| Source Call | Compiler-Generated Concrete Function | Runtime Dispatch Cost |
|---|---|---|
| `double_score(&quiz)` | `double_score::<Quiz>(item: &Quiz) -> u32 { item.raw * 2 }` | **0 bytes vtable, 0 indirect jumps** (inlined to `40 * 2 = 80`) |
| `double_score(&bonus)` | `double_score::<Bonus>(item: &Bonus) -> u32 { item.0 * 2 }` | **0 bytes vtable, 0 indirect jumps** (inlined to `15 * 2 = 30`) |

**Key insight:** You wrote **one** abstract function, yet the CPU executes **two** concrete, inlined instructions with zero dynamic lookup—identical to writing two separate functions by hand!

### Worked Example 2: Checking the Orphan Rule on 4 `impl` Blocks by Hand

Suppose your crate defines `trait Summarize` and `struct Invoice`, while `std::fmt::Display` and `Vec<T>` come from the standard library. Test which `impl` blocks compile:

| Implementation | Is Trait Local? | Is Type Local? | Verdict |
|---|---|---|---|
| `impl Summarize for Invoice` | Yes | Yes | **Allowed ✓** |
| `impl Summarize for Vec<String>` | Yes | No | **Allowed ✓** (local trait!) |
| `impl Display for Invoice` | No | Yes | **Allowed ✓** (local type!) |
| `impl Display for Vec<String>` | No | No | **Rejected ✗** (orphan rule: wrap in `struct Report(Vec<String>)`!) |

### Deep-Dive Explanation: How Trait Bounds, Default Methods, and Blanket Impls Fit Together (Read Slowly)

#### Step 1: Separate the contract from the data
A `trait` declares *what* operations a type must support (`fn normalize(&self) -> String`) without dictating *how* the type stores its fields in memory. Because no hidden vtable pointer is embedded inside the struct, `std::mem::size_of::<Invoice>()` never grows when you implement 20 traits for `Invoice`.

#### Step 2: Use default methods to shrink boilerplate
Whenever one method can be expressed purely in terms of required methods (like `Iterator::count`, `map`, and `filter` all building on `Iterator::next`), give it a **default body** inside the trait. Implementors write one method and inherit dozens for free—while retaining the right to override any default with a faster specialized version.

#### Step 3: Let `where` clauses keep generic signatures readable
Simple bounds fit inline (`fn clean<T: Normalize>(x: &T)`), while multi-trait bounds belong in a `where` clause (`where T: Normalize + Clone + Debug`). Both desugar to the exact same compile-time constraint checked *at the call site* rather than inside the generic body.

#### Step 4: Unlock ecosystem-wide power with blanket `impl`s
A blanket implementation like `impl<T: Display> ToString for T` automatically grants `.to_string()` to every type that implements `Display`—even types written ten years from now! That is why a single well-chosen trait bound makes Rust libraries compose effortlessly.
